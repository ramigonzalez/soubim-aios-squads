# Story 12.10 — Private Meetings, Explicit Milestone Publishing

**Story ID:** 12.10
**Epic:** E12 — Organizations & Client Access
**Priority:** High | **Effort:** 5–8 SP (estimate)
**Status:** Draft
**Type:** Feature (security, product rule)
**Requested by:** Rami — "meetings start as **Private** on the project history, and whatever is added to Milestone can be shared or not. But it's not automatically Public."

---

## Story

As an **organization admin**, I want my meetings to be **Private** by default and to **publish individual milestones explicitly** to the public share link, so that marking something as a milestone never exposes it to the internet by accident.

## Context (current behaviour, verified)

- **Two levels today (12.4).** `sources.visibility` is `internal` | `shared`, default `internal` (`013_story_12_4`). `shared` means "every organization on the project" (12.3), never the internet. Items inherit their source's visibility (`visible_items_filter` in `app/services/access.py`). Switch: `PATCH /api/sources/{id}/visibility` (owner/admin of the meeting's organization), UI in `MeetingVisibilityControl.tsx`, badge in `VisibilityBadge.tsx` ("Interna" / "Compartilhada").
- **Public link.** `POST/GET/DELETE /api/projects/{id}/milestones/share` (`app/api/routes/shared_links.py`, `SharedLink` model, project `admin` of the owner organization). The anonymous `GET /api/shared/milestones/{token}` uses `public_items_filter`: milestones (`project_items.is_milestone`) **of `shared` meetings**. So "shared with the project" silently also means "public if someone marks it milestone".
- **Milestone toggle** (`PATCH /api/projects/{id}/items/{item_id}`, `is_milestone`) is project `admin` only (owner organization), see the 12.2/12.4 route coverage.
- **Open points this story closes:** 12.4 Assumption 5 and Security finding 5 (a public link can publish a partner organization's shared milestones), and the effect of the internal backfill on existing links: **existing public links currently show no milestones** until the owner shares the meetings.

## Target

Three separate questions, three separate controls:

| Question | Control | Audience |
|----------|---------|----------|
| Who sees the meeting? | Meeting visibility: **Privada / Private** (owner organization only) or **Compartilhada com o projeto / Shared with project** (every organization on the project, never the internet) | organizations |
| What is a milestone? | `is_milestone` (unchanged) | the organizations that can see the item |
| What is on the public link? | **Published** flag per milestone, set explicitly | anonymous |

A milestone is on the public share link **only if it was explicitly published**. Marking a milestone never publishes it, and sharing a meeting with the project never publishes its milestones.

## Acceptance Criteria (draft)

- [ ] **Rename** in pt-BR / en: `internal` → **Privada / Private**; `shared` → **Compartilhada com o projeto / Shared with project**. Update `VisibilityBadge`, `MeetingVisibilityControl`, `FathomImportDialog`, upload dialogs and i18n keys (`common`, `meeting`, `integrations`). API/DB values stay `internal` / `shared` unless the architect decides otherwise (Open question 4). The confirmation text says plainly that "shared" reaches every organization on the project and **never the internet**.
- [ ] New meetings of every source (Fathom import, manual upload, Tactiq webhook, document upload) start **Private**. A Fathom importer who is admin may still pick Shared at import (13.4 rule unchanged).
- [ ] `project_items.published_at` (nullable timestamp) + `published_by` (user). A milestone is public only when `is_milestone` **and** `published_at IS NOT NULL`. Migration: next free number after `018_story_12_8_email_google_login` (`019_story_12_10`, renumber if another story lands first).
- [ ] `PUT/DELETE /api/projects/{id}/items/{item_id}/publish` (or a field on the existing PATCH): sets / clears publishing. Allowed only for a milestone that is visible to the caller, `approved` (12.6), and covered by the publishing rule (Open question 1). Un-marking the milestone clears the publication.
- [ ] `public_items_filter` returns only published milestones and no longer depends on the source visibility (a Private meeting's milestone can be published).
- [ ] **Publishing never reveals the private meeting.** The public payload is an explicit `PublicMilestone` schema with the fields chosen as publishable (see Dev Notes) and **no** source id, source title, meeting date, participants, recording or transcript link for a Private meeting.
- [ ] Other organizations on the project (12.3) are unaffected: they still see only Shared meetings; publishing a Private meeting's milestone does not make the meeting or the item visible to them.
- [ ] UI: in the Milestone timeline and the item drilldown, a "Publicar no link público / Publish on public link" toggle with a confirmation that states exactly what becomes public, and a "Publicado / Published" badge. The share-link screen lists the published milestones (a preview of what the link shows).
- [ ] **Migration of existing links.** Existing share links keep working. Recommended rule: nothing is published automatically; the share-link screen shows "0 publicados" and a "Revisar e publicar" list of current milestones. No silent backfill to published (it would re-publish what 12.4 hid).
- [ ] Publishing and un-publishing record who and when (`published_by` / `published_at`, plus an event row if an audit log exists by then).
- [ ] Isolation tests: anonymous link shows only published milestones; a published milestone of a Private meeting exposes no source data on the link nor to a partner organization; un-publish removes it immediately; a contributor organization cannot publish the owner's items; mutation check (make `public_items_filter` ignore `published_at`, tests must fail).
- [ ] Update 12.4 `Assumptions & gaps` item 5 and Security finding 5 with a pointer to this story.

## Dev Notes

- **Who may publish.** The link belongs to the project owner organization (`shared_links.py`). Safer phase-1 rule: only the **owner organization's admins** publish, and only milestones they can see. Letting a contributor (DIMAS) publish its own milestone to a link souBIM created is a product decision (Open question 1). Reviewers (12.7): proposal is no; publishing is irreversible once copied, so keep it to `ADMIN_ROLES` like `can_change_visibility`.
- **Review status (12.6).** Public links already see `approved` only; keep it and test it.
- **Published content.** Today the public endpoint reuses the item serializer. Define an explicit `PublicMilestone` model so a new internal field never leaks by default. Content options: (1) title + statement only (recommended default), (2) + "why" (often holds names, prices, conflicts), (3) + source title/date (only for Shared meetings). Recommend (1) with an opt-in for "why".
- **Rename vs. API values.** Renaming stored values touches the check constraint, `access.py`, 13.4 import rows, tests and frontend types. Recommend UI/i18n only in phase 1.
- **Affected code:** `app/api/routes/shared_links.py`, `app/services/access.py` (`public_items_filter`), `app/api/routes/project_items.py` (publish route, milestone un-mark), `app/database/models.py` (`ProjectItem`), `app/api/models/project_item.py`; frontend milestone timeline, item drilldown, share-link UI (8.4), `VisibilityBadge`, `MeetingVisibilityControl`, `FathomImportDialog`, i18n files.
- **Risks:** an anonymous endpoint is the highest-impact leak surface; needs an @architect security review like 12.2/12.4. Existing links staying empty is a visible change: tell souBIM before deploy.
- **Tests:** extend `tests/unit/test_meeting_visibility.py`; new `tests/unit/test_milestone_publishing.py`.

## Out of scope (phase 2)

- Several links showing different sets of milestones; expiry per milestone.
- Publishing non-milestone items or whole meetings.
- Per-item visibility for manual items (12.4 Assumption 2).
- Renaming the stored enum values.
- Notifying other organizations when something is published.
- Branded public pages (see 12.12).
