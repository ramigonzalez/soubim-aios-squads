# Story 12.11 — Orphaned Meetings After Unsharing

**Story ID:** 12.11
**Epic:** E12 — Organizations & Client Access
**Priority:** Medium | **Effort:** 5–8 SP (estimate)
**Status:** Draft
**Type:** Feature (data lifecycle, security)
**Requested by:** Rami — decided **option (b)**: the removed organization's admins can see and delete their orphaned meetings.

---

## Story

As an **admin of an organization that was removed from a project**, I want to see and delete the meetings (and their items) my organization created there, so that private content is not left behind where nobody can reach it, while a later re-share restores everything.

## Context (current behaviour, verified)

- Example: DIMAS is a contributor on D/SEASON and uploads a Private meeting "DIMAS internal budget". souBIM removes DIMAS from the project (`DELETE /api/projects/{id}/organizations/{organization_id}`, `unshare_project` in `app/api/routes/project_organizations.py`). The route only deletes the share row.
- After that, `project_access_by_organization` gives DIMAS no access, so the meeting is invisible to DIMAS (internal sources are visible only through the owner organization's access to the project). souBIM cannot see it either (internal to DIMAS, 12.4). **Nobody can see or delete it.** It is 12.4 Security finding 7 (open, "cleanup policy — @po") and 12.3 Assumption 10 (share removal keeps `project_members` rows; re-sharing restores them).
- The meeting rows keep `sources.owner_organization_id` = DIMAS. Items follow (`project_items.source_id`, `extraction_run_id`, 13.7 runs). Fathom imports keep `fathom_imports.owner_organization_id`.
- **Recordings** live under the **project owner's** organization key prefix, `org/<project owner org>/sources/<source_id>/recording.<ext>` (`org_id_for_source`, `recording_key`; 12.4 Assumption 8). A deleted share does not move them.
- Deleting a meeting today: `DELETE /api/ingestion/{id}` requires project `admin` through `require_source_access(admin)` (owner organization). Does it remove the storage object? Verify in `app/api/routes/ingestion.py` and `app/services/storage.py` (`delete`) before coding.

## Decision

**Option (b)** (Rami): DIMAS admins see and delete their orphaned meetings from their **organization settings**. Keep **option (a)** behaviour too: the meetings are not deleted automatically, and re-sharing the project restores them to the project view as they were (visibility unchanged, items and runs intact).

## Acceptance Criteria (draft)

- [ ] New read model "orphaned meetings" of an organization: sources with `owner_organization_id = my organization` on projects the organization has **no** current access to (no `project_organizations` row, not the owner). `GET /api/organizations/{id}/orphaned-meetings` (owner/admin of that organization only, `require_org_admin`): list with project name, title, date, source type, item count, has recording, size if known. **Nothing about the project beyond its name and the meeting's own data** (no other organization's meetings, no counts of others' items).
- [ ] Settings → "Reuniões órfãs / Orphaned meetings" in the organization settings, visible only to org owner/admin, only when the list is not empty. Explains: the project owner removed access; these meetings are only visible to you; you can delete them, or ask to be re-added.
- [ ] `DELETE /api/organizations/{id}/orphaned-meetings/{source_id}` and a bulk variant: owner/admin of the meeting's organization only. Deletes the Source, its items, extraction runs, jobs and Fathom import row (cascade, 13.4 / 13.7), and the **recording object** in storage (see Dev Notes). 404 if the meeting is not an orphan of that organization (never lets an admin delete a meeting on a project the organization can still access through this route; use the normal project route for that).
- [ ] Re-sharing the project (`POST /api/projects/{id}/organizations`) restores the meetings: they appear again with their stored visibility. No migration of rows needed. A test covers share → upload private meeting → unshare → meeting invisible in project routes and listed as orphan → re-share → visible again, not listed as orphan.
- [ ] While orphaned, the meetings are excluded from every project query of **all** organizations (no change: already internal). Add a regression test that the project owner never sees them, and that `visible_items_filter` and the public link do not include them.
- [ ] **Audit trail:** each delete writes an event row (who, organization, project id and name, source id and title, item count, recording deleted yes/no, time) in a new `audit_events` table (or the existing one if present by then). The unshare itself also records who removed whom. Events survive the deletion of the source and project (store ids/names as plain values, no FK cascade).
- [ ] **Storage deletion rule:** the recording of a deleted meeting is deleted from storage by the same operation. Because the key is under the project owner's organization, the delete runs with platform credentials on behalf of the meeting's organization; it must delete **only** `org/*/sources/<that source_id>/` (the source id is a UUID, so the prefix is unique). Failures to delete the object do not block the delete: they are logged and retried by a cleanup job (13.2 jobs table), and the audit event notes it.
- [ ] Extraction runs and items: removed with the Source (cascade). Items that were published or marked as milestones (12.10) disappear from public links immediately. Confirm there are no foreign references (digest, shared link snapshots) left dangling.
- [ ] Tests: orphan list shows only the caller organization's meetings; a member (non-admin) gets 403; another organization's admin gets 404; delete removes source, items, runs, import row, and calls storage delete for that source prefix only; delete is idempotent; storage failure does not fail the request and is retried; re-share restores; audit rows written.
- [ ] Update 12.4 Security finding 7 and 12.3 Assumption 10 with a pointer here.

## Dev Notes

- **Detecting orphans** needs a query over `sources` joined to `projects` and `project_organizations`: orphan = `owner_organization_id = :org` and the project is not owned by `:org` and no `project_organizations` row for `:org`. The project owner organization's own sources are never orphans. Index: `idx_sources_owner_org` exists.
- **Who deletes the recording.** Rami's decision gives DIMAS the delete right on its meeting; the object sits under souBIM's prefix. Proposal: the backend deletes it (it holds the storage credentials), scoped by source id, and the audit event records it. The project owner never gets access to that object. If 13.13 / 12.4 Assumption 8 later moves keys to the source owner's organization prefix, this gets simpler; this story must not depend on it.
- **Project deleted while orphans exist.** `sources.project_id` cascade: deleting a project would delete the orphaned meetings of other organizations. Out of scope here, but check the project archive/delete behaviour and flag it (data of another organization disappears silently).
- **What about the reverse** (the project owner organization leaves or is deleted)? Not covered: owner organizations cannot be removed from their own project today.
- **Frontend:** a page under organization settings (next to `TeamSettings.tsx`), reusing the confirm dialog pattern from `MeetingVisibilityControl`. Delete confirmation lists what is deleted (meeting, N items, recording).
- **Export before delete** is phase 2 (below); the phase-1 confirmation text states that deletion is permanent.
- **Risks:** destructive endpoint on a multi-tenant boundary; needs @architect review. Be explicit that the route works only for orphans, so it cannot be used to delete a meeting in a project the organization still shares.

## Out of scope (phase 2)

- **Export / download before deleting** (transcript, items as CSV/JSON, recording link). Recommended as the first follow-up; until then the dialog says deletion is permanent.
- Automatic expiry/purge of orphans after N days; reminder emails to the removed organization.
- Transferring an orphaned meeting to another organization or to a new project of the removed organization.
- A notification to DIMAS when souBIM removes the share (today none).
- Protection of project deletion against removing other organizations' data.
- Orphan handling for `project_items` without a source (manual items, 12.4 Assumption 2) owned by the removed organization: **include in phase 1 only if trivial** (same ownership column), otherwise phase 2.
