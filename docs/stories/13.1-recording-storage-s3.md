# Story 13.1 — Recording Storage (S3-Compatible)

**Story ID:** 13.1
**Epic:** E13 — Recording Ingestion
**Priority:** High | **Effort:** 5 SP (estimate)
**Status:** Ready for Review
**Type:** Feature
**Requested by:** Rami — "save the recordings in Cloudflare R2"

---

## Description

Recordings are stored on the API server's disk today (`uploads/recordings/<source_id>.<ext>`, Story 7.13) — fine for one local pilot, not for production (761 MB per 98-min meeting, multiple servers, backups). Move recording storage to **private S3-compatible object storage**: SeaweedFS in local dev (Docker), Cloudflare R2 or Backblaze B2 in production — same code, different settings.

## Acceptance Criteria

- [x] Storage service over the S3 API (boto3): put (multipart), stream-in from a URL, head, delete, signed GET link (expiring)
- [x] Settings `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_BUCKET`; bucket private (no anonymous access)
- [x] Object keys namespaced by organization: `org/<org_id>/sources/<source_id>/recording.mp4`
- [x] Meeting viewer streams from a **signed storage link** (Range/seek works) instead of `GET /api/recordings/{id}` from disk; access still checked before issuing the link (12.2)
- [x] Size guard (configurable max per file; per-organization quota deferred, see Assumptions & gaps) and lifecycle rule documented (e.g. delete originals N days after processing)
- [x] `docker-compose.yml`: SeaweedFS service for local dev
- [x] Migration script: move existing files from `uploads/recordings/` to storage

## Dev Notes

- **Proven by spike** (`data/tools/storage/s3_test.py`, 2026-10-05): private bucket (anonymous 403), Fathom → storage streaming without a local file, signed links with Range (206) and expiry, 761 MB multipart, browser seek to 33:40.
- MinIO no longer publishes free Docker images (Docker Hub and quay.io refused) — use `chrislusf/seaweedfs` with an `-s3.config` identities file.
- **Open decision:** production provider — R2 (no egress cost; needs a card on file even for the free 10 GB) vs Backblaze B2 (10 GB free). ~76 GB per 100 meetings ≈ $1/month either way. Optionally store audio-only (~50 MB/meeting) for processing.
- Reuse the signing pattern and tests from `app/services/recordings.py` / `tests/unit/test_meetings_api.py` (7.13).

## Assumptions & gaps

- **Provider undecided (R2 vs B2)** - generic `S3_*` settings; SeaweedFS in dev. Alternative: hard-code R2 (not chosen: switching later would need code changes).
- **Local-disk fallback kept** - storage is "enabled" only when all `S3_*` are set; otherwise (or if the object is missing or storage errors) the meeting endpoint uses the 7.13 local file + HMAC link. Alternative: make storage required (simpler code, but dev without SeaweedFS breaks).
- **Presigned URL lifetime 6 h** - same as the previous HMAC links (`LINK_TTL_SECONDS`).
- **Size guard is per file only** (`RECORDING_MAX_BYTES`, default 2 GB; applied by `put_file`, `put_stream_from_url` and the attach script). The per-organization quota from the draft AC is not implemented (needs usage accounting; follow-up).
- **Org fallback** - projects without `owner_organization_id` use `org/unknown/...`. If a project later gets an org, its old object is not found under the new prefix (re-upload or copy the key).
- **Key lookup by prefix** - the extension is not stored in the DB, so the endpoint does one `list_objects_v2` on `org/<org>/sources/<id>/recording.` per meeting view; if storage is unreachable it falls back to local (logged).
- `GET /api/recordings/{id}` (local HMAC route) stays for the fallback; the access check in `get_meeting` is unchanged (12.2 changes it in parallel).
- `put_stream_from_url` is implemented and tested but not yet called by anything (Story 13.4 will).

## Lifecycle rules (documentation only, not automated)

Configure at the provider: expire originals N days after processing (e.g. prefix `org/`, 90 days). R2: bucket Settings > Object lifecycle rules. B2: bucket Lifecycle Settings. SeaweedFS (dev): not needed.

## Local dev setup (SeaweedFS)

1. `cd decision-log-backend && cp docker/seaweedfs-s3.json.example docker/seaweedfs-s3.json`, then replace the placeholder access/secret keys (the real file is git-ignored).
2. `docker compose up -d storage` (S3 API on `127.0.0.1:9000`).
3. Create the bucket once (boto3 `create_bucket`, or `aws --endpoint-url http://127.0.0.1:9000 s3 mb s3://decisionlog-recordings-dev`).
4. Set in `.env`: `S3_ENDPOINT=http://127.0.0.1:9000`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_BUCKET` (see `.env.example`).
5. Attach: `PYTHONPATH=. venv/bin/python scripts/attach_recording.py SOURCE_ID video.mp4`. Migrate old files: `scripts/migrate_recordings_to_storage.py --dry-run`, then without the flag (`--delete-local` removes local copies after a verified upload).
