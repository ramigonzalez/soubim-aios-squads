# Story 12.12 — White Label and Platform Operator

**Story ID:** 12.12
**Epic:** E12 — Organizations & Client Access
**Priority:** Medium | **Effort:** 13+ SP (estimate; split in 2–3 deliveries if needed)
**Status:** Draft
**Type:** Feature (platform, security)
**Requested by:** Rami — he thinks of the app as **white label**; today "souBIM" is hard-coded as special.

---

## Story

As the **platform operator**, I want to create companies, brand the app for each of them and onboard their first owner, without any company (including souBIM) being special in the code, so that DecisionLog can be offered as a white-label product.

## Context (current behaviour, verified)

The 12.1 model comment says "none is special-cased", but the code treats the organization with slug `soubim` as the platform. Every place found with a search for `soubim` / `DEFAULT_ORGANIZATION_SLUG` / `is_platform_admin`:

| 2 | `app/services/access.py` `is_platform_admin` / `require_platform_admin` | **Platform admin = owner/admin of the org with slug `soubim`** |

Other facts: there is **no signup**. Users arrive by invitation (12.5), with email/password or Google sign-in (12.8). In production **nobody exists** until the first user is created some other way (today the seed/souBIM backfill). Per-organization Google Drive is Draft story 12.9; per-organization Fathom exists (13.3).

## Target

1. **Platform operator**: a user-level flag (`users.is_platform_operator`, or a `platform_operators` table), **separate from any tenant organization role**. Operators administer the platform (companies, branding, scheduler, sync); they are not automatically members of any company. souBIM becomes a normal tenant.
2. **Branding per organization** (`organization_branding`): app name, logo, primary/accent colors, custom domain (stored, see phase 2 for serving), email sender name. Applied in the frontend at runtime (login, navigation, page title, favicon, invite and notification emails, public share pages).
3. **Onboarding**: the operator creates a company and invites its **first owner**; the owner then invites their team (12.5).
4. **Bootstrap script** to create the first platform operator and (optionally) the first company + owner in an empty production database.
5. **Per-org integrations**: Drive per organization (links 12.9); Gmail mailbox and matching become per organization (or explicitly "platform mailbox mapped to one organization by configuration, not by slug").

## Acceptance Criteria (draft) — phase 1

### A. Platform operator
- [ ] `users.is_platform_operator BOOLEAN NOT NULL DEFAULT false` (migration next free number after 018). Backfill: users who are owner/admin of the organization with slug `soubim` become operators, so nothing breaks at deploy.
- [ ] `is_platform_admin` / `require_platform_admin` (`access.py`) read the flag, not the slug. Callers 2, 3, 4 and 7 in the table keep working unchanged. `DEFAULT_ORGANIZATION_SLUG` is no longer used for authorization.
- [ ] The frontend no longer compares to `'soubim'`: `GET /api/auth/me` (or the active-organization payload) returns `is_platform_operator`; `TeamSettings.tsx` uses it.
- [ ] Operators cannot read tenant data through the operator role (no bypass of `access.py` for projects/meetings). Operator endpoints expose organization-level data only (name, slug, branding, member counts, owner email), documented in the story as the contract.
- [ ] Tests: slug is irrelevant to authorization (rename souBIM's slug in a test and platform actions still follow the flag); an owner/admin of any tenant is not an operator; an operator who is not in a tenant cannot open that tenant's projects.

### B. Branding per organization
- [ ] `organization_branding`: `organization_id` (unique), `app_name`, `logo_url` (uploaded to storage 13.1 or an https URL; size/type limits), `primary_color`, `accent_color` (validated hex, contrast check against white text), `custom_domain` (nullable, unique, lower-cased; **stored only**, phase 2 serves it), `email_sender_name`. Migration included.
- [ ] `GET /api/branding` returns the branding of the active organization (or by host once domains exist); a public `GET /api/branding/public?org=<slug>` for the login page and public share pages returns only name/logo/colors. Defaults to the platform default ("DecisionLog") when empty.
- [ ] Frontend applies branding at runtime: CSS variables for colors, logo in `Navigation`, `document.title` and favicon, login and invite pages, public milestone pages (8.4/12.10). All hard-coded "DecisionLog" strings in i18n are replaced by an interpolated app name (the list in row 10 of the table).
- [ ] Organization owner/admin edits their own branding in Settings; the operator may edit any. Invitation and notification emails use the sender display name and app name (the sender address stays the platform's, phase 2 for per-tenant domains).
- [ ] Tests for validation (colors, logo type/size), authorization (another organization's admin gets 404), and a frontend test that branding changes the displayed name.

### C. Onboarding
- [ ] Operator screen "Empresas / Companies": list organizations, create a company (name, slug) and invite its first owner (email), re-using 12.5 `POST /api/invitations` with `organization_name`/role `owner`. An invitation for an existing company's first owner is possible too. No self-signup is added.
- [ ] A company with no accepted owner is flagged "convite pendente" with resend/revoke.
- [ ] Audit: who created which company and when.

### D. Bootstrap script
- [ ] `decision-log-backend/scripts/bootstrap_platform.py` (idempotent, safe to run twice): `--operator-email --operator-name` creates the first platform operator (random one-time password printed once, or a password-reset/invite link, and Google sign-in works if the email matches, 12.8); optional `--organization-name --owner-email` creates the first company and its owner. Refuses to create a second operator unless `--force`. Works against the production `DATABASE_URL`, with a dry-run mode and a clear log. Documented in the deploy guide (13.8) and run as a Railway one-off command. No credentials are written to logs or committed.
- [ ] Test the script on an empty database (SQLite and PostgreSQL), including re-run and wrong-state cases.

### E. Per-organization integrations (scoped)
- [ ] **Drive:** depends on 12.9. This story removes the "souBIM service account" assumption from authorization (row 4) only by moving it to the platform-operator flag; real per-organization Drive is 12.9.
- [ ] **Gmail:** make the matching rule explicit configuration instead of the slug: `GMAIL_ORGANIZATION_ID` (or a `mailbox_organization_id` setting) replaces `DEFAULT_ORGANIZATION_SLUG` in `email_matcher.py`. Per-organization mailboxes are phase 2.
- [ ] `DEFAULT_ORGANIZATION_*` stays only as the dev/seed default and the migration backfill, with a comment.

## Dev Notes

- **Deliveries.** Suggested order: (1) operator flag + frontend switch + Gmail setting (small, removes the hard-coding), (2) bootstrap script, (3) onboarding screen, (4) branding. Each can ship alone, and (1)+(2) are the production blockers.
- **Operator vs. tenant.** Keep operator powers narrow (companies, branding of others, scheduler/sync). Do not add an "operator sees everything" mode: it would defeat the isolation work of 12.2–12.4.
- **Branding at runtime.** The SPA is one build; load branding after login from the API and by host for public pages. Avoid a flash of "DecisionLog": render a neutral shell until branding resolves.
- **Custom domain** is stored but not served in phase 1; the frontend resolves branding by host if the host matches a stored domain (works once DNS/TLS exist).
- **Emails.** The email provider is not configured yet (12.5 dev log sender). Branding in emails is applied in the templates so it works once a provider is wired.
- **Risks:** replacing slug-based authorization is security-critical (@architect review, same as 12.2); a bad backfill could lock souBIM admins out of operator functions (verify the backfill on a copy of production data); logo upload is an XSS/size vector (types, size limit, serve from storage, no inline SVG with scripts).

## Out of scope (phase 2)

- Custom domains end to end: DNS verification, TLS certificate issuance, host-based routing.
- Billing, plans, usage metering and limits per company.
- Per-tenant email domain (SPF/DKIM) and per-tenant mailbox polling.
- Per-organization Drive (12.9) and per-organization Gmail connection flow.
- Tenant theming beyond name, logo, two colors (typography, layout, dark mode).
- Self-service company signup, SSO/SAML per company.
- Operator impersonation ("log in as").
