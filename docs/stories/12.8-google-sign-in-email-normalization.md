# Story 12.8 — Sign in with Google & Case-Insensitive Email

**Story ID:** 12.8
**Epic:** E12 — Organizations & Client Access
**Priority:** High | **Effort:** 5 SP (estimate)
**Status:** Ready for Review
**Type:** Feature (auth, security)
**Requested by:** Rami — "Entrar com Google" for invited clients; fixes 12.5 security review item 10 (login compared emails case-sensitively)

---

## Description

1. **Emails are case-insensitive everywhere.** Stored stripped and lowercased, compared with `lower(email)`, and unique on `lower(email)` in the database. An invitee who types `New@X.com` at login now gets in.
2. **Sign in with Google** (OpenID Connect, authorization code flow + PKCE, scopes `openid email profile`). It only signs in **existing active users** whose email matches. From an invitation page it can also accept the invitation: the Google email must equal the invited email, and a new account is created when needed. **No open signup.**

## Acceptance Criteria

### Case-insensitive email
- [x] Login, user creation (ORM validator on `User.email`), invitations, seed (through the validator) and lookups normalize with strip + lowercase (`app/utils/security.normalize_email`, `auth_service.find_active_user_by_email`)
- [x] Migration `018_story_12_8` (down_revision `017_story_12_7`) lowercases `users.email` (and `organization_invitations.email`), adds the unique index `uq_users_email_lower` on `lower(email)`, and **fails with a clear message listing the colliding emails** when two users share an email ignoring case (nothing is changed)
- [x] Migration tested up → down → up on the throwaway DB `decisionlog_test_mig128` (container `decision-log-backend-db-1`), including the collision failure. The DB was dropped afterwards

### Sign in with Google
- [x] Settings `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`. When any of them is unset the feature is off: `GET /api/auth/providers` → `{"password": true, "google": false}`, the Google endpoints answer 404, and the button is hidden
- [x] ID token verified with the signature (Google JWKS, cached 1 h, refetched on an unknown `kid` at most once a minute), `iss`, `aud`, `exp`/`iat` (60 s leeway), `nonce`, and `email_verified` must be true
- [x] `state` is HMAC-signed (domain-separated JWT secret, like 13.3), expires in 10 min, and is single use (row claimed with a conditional UPDATE, so a replay is rejected before Google is called). `nonce` is random per request and checked in the ID token. The PKCE verifier (S256) is wiped after the exchange
- [x] No token in URLs: the callback redirects to `FRONTEND_URL/auth/google/callback#code=<one-time code>` (fragment, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`). The frontend redeems the code (`POST /api/auth/google/exchange`) together with the **browser key** it kept since start. That call returns the same `TokenResponse` (our JWT) as password login. The code is single use, expires in 2 min, and only its hash is stored
- [x] Login CSRF: a code obtained by someone else cannot be redeemed in the victim's browser (browser key mismatch → 403, and the code is burnt)
- [x] No open signup: unknown email → friendly error. A soft-deleted account is never linked or revived (`account_disabled`)
- [x] Google account binding (security review M2, approved by Rami): the first Google sign-in, by login or by invitation, stores the ID token `sub` in `users.google_sub` (unique). A later Google sign-in with another `sub` for the same email → `google_account_mismatch`; the stored `sub` is never overwritten. A `sub` already bound to another account → `google_account_in_use`. The bind is a conditional `UPDATE … WHERE google_sub IS NULL`, so the first login wins
- [x] Invitation: "Continuar com Google" on `/invite/:token`. The Google email must equal the invited email (`email_mismatch`, and the invitation stays usable). The invitation is accepted for an existing active user, or a new account is created with the name from Google and an unusable random password
- [x] Frontend: "Entrar com Google" on Login, "Continuar com Google" on the invite page, and a `/auth/google/callback` page. i18n pt-BR + en (the parity test passes). `?redirect=` is kept through the round trip and validated again with `safeRedirect`
- [x] Tests use a fake JWKS, signed tokens and a mocked token endpoint (`httpx.MockTransport`), with no real Google call. They cover a valid login, an unverified email, wrong `aud`/`iss`, an expired token, a replayed state, an unknown email, an invitation with a mismatched email, and the provider disabled (plus more, see Verification)

## Flow

```
Login / Invite page ──POST /api/auth/google/start {invitation_token?}──► {url, browser_key}
  (browser_key → sessionStorage)            row: state_nonce, oidc_nonce, PKCE verifier, sha256(browser_key), invitation
      │ window.location = url (Google consent, prompt=select_account, login_hint = invited email)
      ▼
Google ──302──► GET /api/auth/google/callback?code&state          (public; API domain: localhost:8000 / ngrok / Railway)
      verify signed state → claim row once → exchange code + verifier → verify ID token → store verified email
      ──302──► FRONTEND_URL/auth/google/callback#code=<one-time>   or  #error=<reason>
      ▼
GoogleCallback page ──POST /api/auth/google/exchange {code, browser_key}──► TokenResponse (+ organization_id)
      browser key must match → code used once → resolve account (login / invitation) → our JWT
```

Errors (`#error=` from the callback or `detail` from the exchange), each with a pt-BR/en message: `denied`, `invalid_request`, `invalid_state`, `exchange_failed`, `invalid_token`, `email_unverified`, `invalid_code`, `browser_mismatch`, `expired`, `unknown_email`, `account_disabled`, `email_mismatch`, `invitation_gone`, `google_account_mismatch`, `google_account_in_use`.

## Assumptions & gaps

Each item: chosen option — alternatives — who confirms. **All pending confirmation.**

1. **Library: no new dependency** — ID tokens are verified with **PyJWT** (`PyJWK`, RS256, already a dependency, with `cryptography`) and Google's endpoints are called with **httpx** (already a dependency). `google-auth` is installed (Drive) but needs its own transport for JWKS and is harder to fake in tests. — Alt: `google.oauth2.id_token.verify_oauth2_token`. — **@architect** (pending).
2. **Google endpoints hardcoded** (`accounts.google.com/o/oauth2/v2/auth`, `oauth2.googleapis.com/token`, `www.googleapis.com/oauth2/v3/certs`) instead of reading the discovery document on every start. — Alt: fetch `/.well-known/openid-configuration` and cache it. — **@architect** (pending).
3. **Email + Google `sub` binding (first login wins)**: the account is found by its verified email, and the first Google sign-in stores the `sub` in `users.google_sub`. Later Google sign-ins must come from that same Google account; a different `sub` is refused and never overwritten. There is no "unlink Google" yet: an admin clears `google_sub` in the DB if a user legitimately changes Google account. A user whose Google account email changes no longer matches (the lookup is by email). — **Rami** (confirmed 2026-10-06).
4. **`email_verified` is enough**: any Google account (Gmail or Workspace) with a verified email may sign in to the matching user, and the `hd` (Workspace domain) claim is not checked. — Alt: per-organization allowed domains. — **Rami** (pending).
5. **Invitation + new account via Google**: the account is created with the Google `name` (fallback: the email local part) and an unusable random bcrypt password. The person can only log in with Google until a "forgot password" flow exists (12.5 gap 12). — **Rami** (pending).
6. **Browser key in `sessionStorage`**: the flow must finish in the same tab. If the user opens the consent in another tab or the frontend loses `sessionStorage`, they get `browser_mismatch` and start again. — Alt: an HttpOnly cookie on the API domain (does not work with the ngrok/localhost split). — **@architect** (pending).
7. **PKCE verifier stored in plaintext** in `google_login_requests` for at most 10 min (wiped after the exchange). Without the Google code it is useless. Fernet was not used, so `TOKEN_ENCRYPTION_KEY` is not required for login. — **@architect** (pending).
8. **Migration lowercases existing emails irreversibly** (the downgrade keeps them lowercased). The column-level `users_email_key` unique constraint is kept next to the new `lower(email)` index. — **Rami** (pending).
9. **Migration number**: `018_story_12_8` revises `016_story_12_6` because 017 belongs to another branch. **Renumber `down_revision` on merge.** — main session (pending).
10. **Rate limit** on `start` is the in-memory per-IP limiter (20 per 15 min, off when `DEBUG`/`ENVIRONMENT=development`). The exchange is not rate limited (256-bit single-use code). — follow-up with the shared limiter (12.5 gap 6) (pending).
11. **Gap: password login is still offered to Google-only accounts** (it fails with the random password), and there is no "disconnect Google". Not needed while matching is by email. (pending)
12. **Gap: `last_login_at`** is not updated by either login method (pre-existing). (pending)
13. **Google consent screen and ngrok**: `ngrok-free.app` is a public suffix. Google may refuse it as an *authorized domain* when the app is published, but redirect URIs on it work in Testing mode. — **Rami** to confirm while creating the client. Fallback: test with `http://localhost:8000/...`. (pending)

## Security review

Review of the uncommitted branch diff (2026-10-06): OIDC flow, one-time code exchange, account linking, redirects, email normalization + migration `018_story_12_8`, rate limiting. **No Critical or High finding.**

| Severity | Finding | Status |
|---|---|---|
| Medium | **Rate limit keyed on `request.client.host`**: Railway/Docker start uvicorn without `--forwarded-allow-ips`, so behind the edge proxy every user shares the proxy IP. 20 Google starts per 15 min (and the 5 password logins, pre-existing) then apply to everyone, and one client can lock Google sign-in for all users. | Open → 13.11 (trusted client IP from `X-Forwarded-For` behind the known proxy only) |
| Medium | **Account matching by email only** (Assumption 3/4): for a Google account whose address Google does not host (not `@gmail.com`, no `hd` claim), `email_verified` only says the address was verified once. Verified OK (no change):
- **OIDC**: authorization code + PKCE S256 (verifier 96 chars, wiped after the exchange). The `state` is HMAC-SHA256 with a domain-separated key and a 10 min expiry. It is single use through a conditional `UPDATE … WHERE callback_at IS NULL`: two concurrent callbacks serialize on the row lock, and the second sees 0 rows → `invalid_state` before Google is called. A random `nonce` is checked with `compare_digest`.
- **ID token**: the header `alg` must be `RS256` and `jwt.decode(algorithms=["RS256"])` uses an RSA key object, so there is no `none`/HS confusion. The key is looked up by `kid`; an unknown kid refetches at most once a minute. `iss` ∈ {`https://accounts.google.com`, `accounts.google.com`}, `aud` == client id, `exp`/`iat` checked with 60 s leeway (PyJWT also rejects an `iat` in the future). `email_verified` must be `True` or `"true"`, and `sub`/`email` are required.
- **Token endpoint**: non-200, non-JSON, a JSON list or a missing `id_token` → `exchange_failed`. Access tokens are neither stored nor logged, and errors carry only the HTTP status and Google's error code.
- **One-time code**: 256 bits, SHA-256 stored, 2 min TTL. It is burnt atomically (conditional `UPDATE … WHERE consumed_at IS NULL`, so a race has one winner) before the browser key is checked. The browser key hash is compared with `compare_digest`, and a mismatch → 403 with the code burnt. The code is bound to the request row, so it resolves only the email Google verified for that flow. The browser key lives in `sessionStorage` (this tab), is cleared on the callback page, and the fragment is removed with `replaceState`. There are no third-party scripts on the page.
- **Linking**: no open signup. Only an active user (`deleted_at IS NULL`) with the same normalized email can sign in, and a soft-deleted user → `account_disabled`, never revived. On the invitation path, the invitation is bound at start (`invitation_id` on the row, not from the exchange body). The Google email must equal the invited email, and a mismatch leaves the invitation pending. A new account takes its email and role (`client`, membership role from the invitation) and its organization from the invitation, with a bcrypt hash of a random 256-bit secret. An existing (also soft-deleted) email is never duplicated, and concurrent creation → 409. `_claim` keeps single use.
- **Redirects**: the callback only redirects to `FRONTEND_URL/auth/google/callback#…`, with `no-store` and `no-referrer`. `?redirect=` is validated by `safeRedirect` before it is saved and again after the round trip, and the invitation link back uses `encodeURIComponent`.
- **Email normalization**: the `User.email` validator, `authenticate_user`/`find_active_user_by_email`, invitations (create / accept / `account_exists` / `_email_taken`), the seed (lowercase literals through the validator), and `scripts/import_extracted_items.py` all normalize. `/api/auth/me` resolves the user by id from the JWT. Webhooks (Tactiq/Fathom) and the Gmail poller do not match users by email.
- **Migration `018_story_12_8`**, re-tested on the throwaway `decisionlog_test_rev128` (dropped afterwards): `Ana@X.com` + `ana@x.com` → fails with "ana@x.com (2 users)" and stays at 016 with nothing changed. After removing the duplicate, `upgrade head` gives `ana@x.com` and `bob@y.com` (from ` Bob@Y.COM`) and `CREATE UNIQUE INDEX uq_users_email_lower … (lower(email))`, and inserting `BOB@y.com` is rejected by the index. `downgrade 016_story_12_6` removes the table and index, and `upgrade head` again succeeds.

**Merge note (13.11 rate limiting)**: keep a limit on `POST /api/auth/google/start` (today `google_start_rate_limit`: 20 / 15 min per IP, key prefix `google-start:ip:`, off in development, 429 + `Retry-After: 900`). Make sure the new limiter's client IP is the real client behind Railway's proxy. Consider adding `/api/auth/google/exchange` and `/api/auth/google/callback` (per IP, generous) to the new limiter. Also keep `login_rate_limit` on `/api/auth/login`. The route wiring in `app/api/routes/auth.py` imports `google_start_rate_limit` by name.
