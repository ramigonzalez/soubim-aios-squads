# Story 13.3 — Connect to Fathom (OAuth)

**Story ID:** 13.3
**Epic:** E13 — Recording Ingestion
**Priority:** High | **Effort:** 5 SP (estimate)
**Status:** Ready for Review
**Type:** Feature (integration, security)
**Requested by:** Rami — "users authenticate 'connect to Fathom' from our app"

---

## Description

Each user connects **their own** Fathom account from DecisionLog ("Conectar ao Fathom"), so clients import their recordings without going through souBIM's account. The OAuth app ("DecisionLog") is registered once in the owner's Fathom account; Client ID/Secret live only in backend secrets.

## Acceptance Criteria

- [x] `fathom_connections`: user_id, organization_id, access_token & refresh_token (**encrypted at rest**), expires_at, scope, fathom account label/email, connected_at, revoked_at
- [x] `GET /api/integrations/fathom/connect` → Fathom authorize URL with `state` (CSRF, bound to the user); `GET /api/fathom/callback` → validate state, exchange code, park tokens as *pending*; `POST /api/integrations/fathom/confirm` (logged-in user, must match the state's user) → store tokens
- [x] Automatic refresh before expiry (tokens last 24 h); refresh failure marks the connection as needing reconnect
- [x] Settings page: connection status, connected account, "Desconectar" (deletes tokens)
- [x] All Fathom HTTP calls in one client module (`app/integrations/fathom.py`) with tests against recorded responses

## Dev Notes

- **Proven by spike** (`data/tools/fathom/oauth_test.py`, 2026-10-05, owner's own account): authorize `https://fathom.video/external/v1/oauth2/authorize` (`client_id`, `redirect_uri`, `scope=public_api`, `state`, `response_type=code`); token exchange and refresh at `https://fathom.video/external/v1/oauth2/token` — **the docs' `https://api.fathom.ai/external/v1/oauth2/token` was not used; the SDK URL worked**. Tokens: `expires_in=86400`, refresh token returned. API calls: `Authorization: Bearer`, base `https://api.fathom.ai/external/v1`. Token endpoint rate limit: 60 req/min.
- Redirect URLs must be HTTPS: dev uses the ngrok domain `naturally-ethical-shark.ngrok-free.app`; production uses the Railway domain (13.8). Registered in the Fathom app form (production + development URLs).
- **Untested — run before implementing:** can *another* Fathom account connect to the app while it is in development mode, or does Fathom require approval first?
- Encryption key in secrets (e.g. Fernet); never log tokens.

## Implementation

- **Settings** (`app/config.py`): `FATHOM_CLIENT_ID`, `FATHOM_CLIENT_SECRET`, `FATHOM_REDIRECT_URI`, `TOKEN_ENCRYPTION_KEY` (Fernet), `FRONTEND_URL` (default `http://localhost:5173`). The integration is enabled only when the first four are set and the key is a valid Fernet key; otherwise `connect`/`callback` answer 404 and the status endpoint returns `configured: false` (the settings page shows "not available on this server").
- **Tables** (migration `008_story_13_3`, down_revision `007_story_13_2`; downgrade drops both):
  - `fathom_connections`: `id`, `user_id` (unique, FK users, cascade), `organization_id` (FK, the user's primary organization at connect time), `access_token_enc`, `refresh_token_enc`, `expires_at`, `scope`, `account_label`, `connected_at`, `revoked_at`.
  - `fathom_pending_connections`: `id`, `nonce` (unique, opaque id sent to the frontend), `state_nonce` (unique — makes each OAuth state single use), `user_id` (from the state, FK users, cascade), `access_token_enc`, `refresh_token_enc` (Fernet, wiped once used), `token_expires_at`, `scope`, `expires_at` (= created + 10 min, indexed), `consumed_at`, `created_at`.
- **Client** `app/integrations/fathom.py` (the only module calling Fathom, `httpx`): `authorize_url(state)`, `exchange_code`, `refresh_tokens`, and `FathomClient(db, connection)` with `list_meetings(cursor, include_transcript, **filters)` → `MeetingsPage(items, next_cursor)`, `request_download(recording_id)`, `download_status(recording_id, download_id)`. Refreshes 60 s before expiry and once on an API 401 (a second 401 raises, no loop); tokens that no longer decrypt (key changed) mark the connection as needing reconnect; recording/download ids are validated (`[A-Za-z0-9_-]{1,128}`) before going into URL paths; malformed token responses raise `FathomAPIError`; a 400/401/403 from the token endpoint sets `revoked_at` (= needs reconnect) and raises `FathomReconnectRequired`; 5xx/network errors raise without marking. Errors carry the HTTP status and Fathom's `error` code only — never tokens, codes or secrets.
- **State**: `<base64url payload>.<HMAC-SHA256>` with the JWT secret (domain-separated, constant-time compare), payload = user id + random nonce + expiry (10 min). Single use: the nonce is recorded in `fathom_pending_connections.state_nonce`; a replayed state is rejected before any call to Fathom.
- **Two-step connect (login-CSRF protection)**: the callback is public and served on the API domain (ngrok/Railway), so it cannot see who is logged in on the frontend (localhost/another origin — no shared cookie). It therefore never writes `fathom_connections`: it parks the encrypted tokens in a pending record and redirects to the frontend with an opaque nonce; the frontend confirms with the user's JWT and the backend accepts only when the logged-in user is the one named in the state. An attacker who sends their own consent link to a victim gets a pending record the victim's browser cannot confirm (403, tokens wiped) and the attacker never sees the nonce. Expired pending records are deleted opportunistically on every callback/confirm (no cron).
- **Routes** (`app/api/routes/fathom.py`):
  - `GET /api/integrations/fathom/connect` (auth) → `{url}`; the frontend sends the browser there (a plain link cannot carry the JWT header).
  - `GET /api/fathom/callback` (public path in `auth_middleware`) → verifies the state (signature, expiry, not used before), exchanges the code, stores the encrypted tokens in `fathom_pending_connections`, then 302 to `FRONTEND_URL/settings/integrations?fathom=pending&nonce=<opaque>` (no token/code in the URL; `Cache-Control: no-store`, `Referrer-Policy: no-referrer`) or `?fathom=error&reason=denied|invalid_request|invalid_state|exchange_failed|fathom_error`. Redirects only ever go to `FRONTEND_URL`.
  - `POST /api/integrations/fathom/confirm {nonce}` (auth) → moves the pending tokens into `fathom_connections` (replacing any previous connection), wipes them from the pending row, labels the account with the recorder email from one `GET /meetings` call (best effort) and returns the status. 403 when the state named another user (pending tokens wiped), 410 when expired (row deleted), 404 when unknown or already used.
  - `GET /api/integrations/fathom` → `{configured, connected, needs_reconnect, account_label, connected_at}`.
  - `DELETE /api/integrations/fathom` → 204, deletes the row (tokens); 404 when not connected.
- **Frontend**: page `/settings/integrations` ("Integrações"; gear icon in the navigation bar, all roles) with not-connected / connected / needs-reconnect / not-configured states, "Conectar ao Fathom", "Reconectar", "Desconectar" (with confirmation) and the callback result banner. On `?fathom=pending&nonce=…` it calls confirm once (guarded against StrictMode double effects), then replaces the URL with `?fathom=connected` or `?fathom=error&reason=other_user|expired|confirm_failed` (the nonce leaves the address bar) and shows a specific message for 403/410. New i18n namespace `integrations` (pt-BR + en), `nav.integrations`.

## Assumptions & gaps

Each item: chosen option — alternatives — who confirms.

- **Fernet key management** — one `TOKEN_ENCRYPTION_KEY` env var on API and worker; rotating it makes stored tokens unreadable (users reconnect). Alternatives: `MultiFernet` with key rotation, or a KMS. Confirm: Rami (prod secret handling, 13.8).
- **One connection per user** (unique `user_id`; reconnecting replaces it). `organization_id` is recorded (primary organization at connect time) but the connection is personal. Alternative: one per (user, organization) once users switch organizations (12.5), or one shared per organization. Confirm: Youval/Rami — matters when a user belongs to several organizations.
- **`revoked_at` doubles as "needs reconnect"** — set when Fathom rejects the refresh token; no separate column. Alternative: `needs_reconnect` boolean + a separate revocation timestamp. Confirm: Rami (low stakes).
- **Disconnect deletes the row locally only** — the spike found no Fathom revoke endpoint, so the grant stays listed in the user's Fathom settings until they remove it there. Confirm: Rami (check Fathom docs for a revoke endpoint).
- **Login CSRF closed with a two-step confirm** (see Implementation) — chosen over a browser-bound cookie because the callback (ngrok/Railway API domain) and the frontend are different origins. Consequence: if the user's frontend session expired while on Fathom, `ProtectedRoute` sends them to `/login` and the pending request is lost (expires in 10 min) — they click "Conectar" again. Consumed pending rows are kept (without tokens) until they expire so the state cannot be replayed, then deleted opportunistically.
- **Settings page location** — new `/settings/integrations`, reached by a gear icon in the navigation bar (there is no user menu yet). Alternative: a dropdown user menu. Confirm: UX/Rami.
- **Concurrent refresh** — if the API and the worker (13.4 import jobs) refresh the same connection at the same moment and Fathom rotates refresh tokens, one may be invalidated and the connection marked needs-reconnect. Not handled (would need `SELECT … FOR UPDATE` around the refresh). Revisit in 13.4.
- **Account label** — taken from `recorded_by.email` of the first listed meeting (Fathom has no "who am I" endpoint in the spike); empty for accounts with no meetings yet.
- **Untested: another Fathom account connecting to a dev-mode OAuth app** — still open (only the owner's account was tested in the spike). Confirm: Rami, by connecting a second account (see Verification).
- No real Fathom call was made while implementing; all tests use `httpx.MockTransport` with response shapes from the spike.

## Security review

Review of the whole branch diff (2026-10-06). Fixed items have tests in `tests/unit/test_fathom.py` / `IntegrationsSettings.test.tsx`.

| Severity | Finding | Status |
|---|---|---|
| High | Login CSRF / account binding: the public callback stored tokens for the user named in the state, so an attacker's consent link approved by a victim attached the victim's Fathom account to the attacker | **Fixed** — two-step confirm (pending record + authenticated confirm bound to the state's user; mismatch → 403 and tokens wiped) |
| Medium | OAuth state not single use (replayable within 10 min) | **Fixed** — `state_nonce` unique in `fathom_pending_connections`; replay rejected before calling Fathom |
| Medium | Recording/download ids interpolated into Fathom URL paths unvalidated (`../` could reach other Fathom endpoints with the user's token once 13.4 passes external ids) | **Fixed** — ids validated against `[A-Za-z0-9_-]{1,128}` |
| Medium | Tokens unreadable after a `TOKEN_ENCRYPTION_KEY` change raised an unhandled `TokenEncryptionError` (500) | **Fixed** — connection marked needs-reconnect |
| Low | Non-JSON / malformed 200 from the token endpoint raised `ValueError` (500 on callback) | **Fixed** — `FathomAPIError` → `exchange_failed` |
| Low | Nonce left in the address bar / Referer after the callback | **Fixed** — frontend replaces the URL after confirm; callback redirects send `Referrer-Policy: no-referrer`, `Cache-Control: no-store` |
| Medium | Concurrent refresh by API and worker may invalidate a rotated refresh token (marks needs-reconnect) | Open — revisit in 13.4 (`SELECT … FOR UPDATE`) |
| Medium | Disconnect deletes tokens locally only; the grant stays active at Fathom (no revoke endpoint found) | Accepted — users can remove it in Fathom settings |
| Low | Single Fernet key, no rotation (`MultiFernet`) | Accepted for the pilot (see Assumptions) |
| Low | Status shows "connected" for tokens that no longer decrypt until the next API use marks needs-reconnect | Accepted |
| Low | Pending request lost if the frontend session expired during consent (redirect to `/login` drops the query) | Accepted — user reconnects |
| Info | Verified OK: Fernet at rest, tokens/codes/secrets absent from logs, URLs, errors and responses; HMAC with `hmac.compare_digest`, domain-separated key, expiry; redirects only to `FRONTEND_URL`; all `/api/integrations/fathom*` routes need auth (middleware test), only the callback is public; status/delete scoped to the current user; refresh retries once on 401 (no loop); cursor/filters go through httpx query encoding; integration disabled (404 / `configured: false`) when the key is missing or invalid | — |

### Live test with ngrok (Rami)

1. In `decision-log-backend/.env` add `TOKEN_ENCRYPTION_KEY` (generate: `python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`) and make sure `FATHOM_REDIRECT_URI=https://naturally-ethical-shark.ngrok-free.app/api/fathom/callback` (same string as in the Fathom app). `FRONTEND_URL` defaults to `http://localhost:5173`.
2. `cd decision-log-backend && venv/bin/alembic upgrade head` (or let dev `create_all` create the table).
3. Start the app (`./dev.sh`) and the tunnel: `ngrok http --url=naturally-ethical-shark.ngrok-free.app 8000`.
4. Log in at `http://localhost:5173`, click the gear icon → **Integrações** → **Conectar ao Fathom**, approve on Fathom. You should land on `/settings/integrations?fathom=pending&nonce=…`, which confirms automatically and switches to `?fathom=connected` showing "Conectado como <your email>".
5. Check the DB row: `access_token_enc` is ciphertext. **Desconectar** removes it.
6. Open question to close: repeat step 4 logged in as another DecisionLog user with a *different* Fathom account to learn whether a dev-mode Fathom app accepts other accounts.
