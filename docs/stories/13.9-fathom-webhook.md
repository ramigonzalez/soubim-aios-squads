# Story 13.9 — Fathom Webhook (Push)

**Story ID:** 13.9
**Epic:** E13 — Recording Ingestion
**Priority:** Low | **Effort:** 5 SP (estimate)
**Status:** Ready for Review
**Type:** Feature (integration, security-sensitive: public endpoint)
**Requested by:** Rami — automate Fathom calls being sent to the platform

---

## Description

Optional automation after browse-and-pick (13.4) works: Fathom calls DecisionLog when a connected account's meeting is ready (`new_meeting` webhook), and the meeting lands in Ingestão as **pending** — never auto-imported without the user having opted in, and never into a project the user cannot write to.

## Acceptance Criteria

- [x] `POST /api/fathom/webhook/{connection_id}`: verify `webhook-id` / `webhook-timestamp` / `webhook-signature` (Standard Webhooks, HMAC-SHA256 over the raw body, constant-time compare, several signatures accepted), reject replays (timestamp ±5 min) and duplicate `webhook-id`s (idempotent) — see Assumptions 1
- [x] Webhook registered per connection via the Fathom API when the user opts in (and deleted when they opt out or disconnect) — **untested against live Fathom** (Assumptions 2)
- [x] Meeting → project mapping: the connection's **default project** (+ visibility, internal default); a meeting with no default project (or an unusable one) waits in an "Unassigned" list for a person to pick a project or discard — per-organization **rules are not built** (Assumptions 3)
- [x] Download via the `fathom_import` job (13.4): the webhook creates the same `fathom_imports` row + job a manual import does
- [x] Opt-in per user; off by default
- [x] Frontend: auto-import settings on the Fathom card (enable, default project, visibility); Unassigned list with assign / discard on the Fathom meetings page; pt-BR + en

## Dev Notes

- Requires a public HTTPS backend (13.8 / ngrok in dev). The URL registered at Fathom is the origin of `FATHOM_REDIRECT_URI` + `/api/fathom/webhook/{connection_id}` — no new setting.
- Fathom's payload could carry transcript/summary/action items; we request none (`include_*` false): the import job reads everything it needs from the user's own Fathom account (13.4), so the webhook only has to say "recording X is ready".

## Implementation

```
Fathom ──POST /api/fathom/webhook/{connection_id} (webhook-id, -timestamp, -signature)──▶ API
  API: connection by id → enabled? secret (Fernet) → timestamp ±5 min → HMAC(raw body) constant-time
       → claim webhook-id (unique per connection) → recording_id from payload
       → default project usable (exists, not archived, user can still write, storage on)?
            yes → start_import (13.4/12.4: owner org = user's acting org on the project, visibility) → fathom_import job
            no  → fathom_unassigned_meetings row (user assigns later / discards)
       → 202 {"status": ...}   (nothing is downloaded in the request)
```

- **Migration** `015_story_13_9` (down `013_story_12_4`): `fathom_connections` + `auto_import_enabled` (default false), `auto_import_project_id` (FK SET NULL), `auto_import_visibility`, `webhook_id`, `webhook_secret_enc` (Fernet, like the tokens); `fathom_webhook_events` (unique `(connection_id, webhook_id)`, pruned after 1 day); `fathom_unassigned_meetings` (unique `(user_id, recording_id)`).
- **Service** `app/services/fathom_webhook.py`: `verify_signature` (secret `whsec_<base64>` → key; signed content `"{id}.{timestamp}.{raw body}"`; header = space-separated `v1,<base64>` list; `hmac.compare_digest` on every candidate; timestamp ≤ 5 min from now either way; id charset/length checked), `register` / `unregister` (Fathom `POST /webhooks`, `DELETE /webhooks/{id}` through `FathomClient`), `process`.
- **Routes** (`app/api/routes/fathom.py`): `PUT /integrations/fathom/auto-import {enabled, project_id, visibility}` (write access to the project; `shared` only for admins — same rules as 13.4), `GET /integrations/fathom/unassigned`, `POST …/unassigned/{id}/assign {project_id, visibility}` (calls the 13.4 import route logic, then removes the row), `DELETE …/unassigned/{id}`, public webhook. `GET /integrations/fathom` now returns `auto_import`. Disconnecting also deletes the webhook at Fathom (best effort). `/api/fathom/webhook/` is added to the auth middleware's public paths.
- **Security properties**: every failure (non-UUID or unknown connection, auto-import off, no/unreadable secret, bad/missing/malformed headers, stale timestamp, wrong signature) answers the same `401 {"detail":"Invalid webhook"}`; body capped at 1 MB (413); secret, signatures, payloads and titles are never logged; the secret is never returned by any endpoint; the signature is checked before any DB write; the event claim and the import/unassigned row commit in one transaction (a crash makes Fathom's retry succeed, not get lost).
- **Frontend**: `FathomAutoImportSettings` (organism, on the connected Fathom card in Integrações), `FathomUnassignedList` (organism, top of the Fathom meetings page; hidden when empty), service/types, i18n `fathom.autoImport.*` and `unassigned.*` (pt-BR + en).

## Assumptions & gaps

Each item: chosen option — alternatives — who should confirm.

1. **Signature scheme taken from the brief, not from Fathom's docs** (no web access for this story): Standard Webhooks headers, `v1,<base64 HMAC-SHA256("{id}.{timestamp}.{body}")>`, secret `whsec_<base64>` (a secret without the prefix is used as plain text). **Not verified against a real Fathom delivery.** — **Rami** (live test; if Fathom signs differently only `fathom_webhook.sign/verify_signature` changes).
2. **Registration via Fathom's API** (`POST /webhooks` with `destination_url`, `triggered_for: ["my_recordings"]`, `include_*: false`; response `{id, secret}`; `DELETE /webhooks/{id}`): request/response shapes follow Fathom's public docs from memory and are **untested live** — tests use `httpx.MockTransport`. Alternative: the user creates the webhook in Fathom's UI and pastes the secret in DecisionLog (no API dependency, more manual). — **Rami** (live test).
3. **No per-organization mapping rules** (the draft story's "calendar title contains D/SEASON → D/SEASON"): the brief asks for default project + unassigned list; rules are phase 2. Today every pushed meeting of an opted-in user goes to the user's single default project or to Unassigned. Cost of rules later: a rules table + matching in `process` (the unassigned flow already exists). — **Rami/@po**.
4. **One webhook, one connection, one user** — the connection id in the URL routes the delivery and its own secret authenticates it; there is no shared/global webhook secret. Reconnecting Fathom keeps the same connection row (and webhook); disconnecting deletes both.
5. **Own recordings only** (`triggered_for: my_recordings`): team recordings shared into the user's account do not trigger it. Alternative: also `shared_team_recordings`. — **Rami**.
6. **Unassigned list is per user and assigns as `internal`** (no visibility choice in that list); switching to shared is possible afterwards in Ingestão (12.4). Alternative: visibility radio like the import dialog. — **@po**.
7. **Unusable default project → Unassigned** (project deleted, archived, user lost write access, or recording storage not configured) instead of a failed import. A default `shared` visibility silently falls back to `internal` if the user is no longer an admin. — **Rami**.
8. **Duplicates**: same `webhook-id` → `{"status":"duplicate"}`; a recording already imported into the default project (e.g. manually) → `duplicate` too, no second import. A recording that is Unassigned is listed once.
9. **Payload fields trusted only after the signature**: `recording_id` (validated `[A-Za-z0-9_-]{1,128}`), `title`/`meeting_title` (trimmed to 255, display only), `recording_start_time`. Anything else is ignored; a signed delivery without a usable `recording_id` is acknowledged (`ignored`) so Fathom does not retry forever.
10. **No rate limiting** on the public endpoint (the in-memory limiter is per instance and unused elsewhere for public routes); unauthenticated requests cost one primary-key lookup and, without a valid signature, nothing else. Alternative: limit at the proxy (Railway/ngrok). — **@architect (security)**.
11. **Retention of delivery ids** is 1 day (replay window is 5 min), pruned on each accepted delivery.
12. **Webhook left registered at Fathom if the deletion fails** (Fathom down / token revoked): the local secret is dropped anyway, so later deliveries are rejected with 401; the orphan webhook can be removed in Fathom's UI.

### Live test (Rami)

Prerequisites: 13.3/13.4 live tests done, `FATHOM_REDIRECT_URI` on the ngrok URL, storage up, `alembic upgrade head` (renumber the migration if 13.7 took 014 first).

1. `./dev.sh` (API + worker + frontend) and `ngrok http --url=naturally-ethical-shark.ngrok-free.app 8000`.
2. Integrações → Fathom card → tick **Importar novas reuniões do Fathom automaticamente**, pick a default project (or none), **Salvar**. Check in Fathom (Settings → API/Webhooks) that a webhook pointing to `https://naturally-ethical-shark.ngrok-free.app/api/fathom/webhook/<connection id>` exists. If Fathom rejects the registration the card shows "O Fathom não conseguiu registrar o webhook" — the API shapes in Assumption 2 need adjusting.
3. Record a short meeting in Fathom (or use Fathom's "test webhook" if available). When processed, the ngrok inspector (http://127.0.0.1:4040) shows `POST /api/fathom/webhook/...` → `202 {"status":"imported"}`; the worker log shows the `fathom_import` job; the meeting shows up in Ingestão as pending (internal).
4. If no signature check passes (401 in the inspector), compare the real `webhook-signature` header with Assumption 1.
5. Save again with **no default project**, record/replay another meeting: it appears under "Reuniões não atribuídas" on the Fathom meetings page; assign it to a project or discard it.
6. In the ngrok inspector use **Replay** on a delivery: same `webhook-id` → `duplicate`; an old one → 401 (stale timestamp). Untick the option and save: the webhook disappears in Fathom and new deliveries get 401.
