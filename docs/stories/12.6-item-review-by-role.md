# Story 12.6 — Item Review: Approve / Reject / Edit by Role

**Story ID:** 12.6
**Epic:** E12 — Organizations & Client Access
**Priority:** Medium | **Effort:** 5 SP (estimate)
**Status:** Ready for Review
**Type:** Feature
**Requested by:** Rami — "approve/reject project items, maybe edit them too, only restricted persons"

---

## Description

Extracted items go straight into Project History today. Reviewers should be able to **approve, reject or edit** each item; edits keep the AI's original so corrections can be compared. Only users with a reviewer-capable role in the owning organization can review.

## Acceptance Criteria (draft)

- [x] Item `review_status` (`pending` / `approved` / `rejected`), `reviewed_by`, `reviewed_at`
- [x] Edit title / statement / why / owner / due date; the original extracted values are kept (e.g. `original` JSON) and viewable
- [x] Only owner-organization `admin`/`owner` (or a `reviewer` role if added in 12.1) can review
- [x] Bulk approve / reject from Project History (bulk API by ids or by meeting; UI: "Aprovar pendentes" per meeting - see gaps)
- [x] Rejected items hidden from History by default (filter to show)

## Dev Notes

- Open decision (with Youval): do non-reviewers and shared organizations see `pending` items (with a badge) or only `approved` ones?
- Interplay with extraction versions (13.7): reviews belong to a version; switching versions shows that version's review state. Carrying reviews across versions is out of scope (matching "the same item" across runs is fuzzy).

## Implementation Notes

- Migration `016_story_12_6` (down_revision `015_story_13_9`): `project_items.review_status` (NOT NULL, server default `approved`, CHECK pending/approved/rejected, indexed), `reviewed_by` (FK users, SET NULL), `reviewed_at`, `original` (JSON). **Backfill: every existing item is `approved`** (the server default fills existing rows), so D/SEASON's 54 items keep showing unchanged. Verified up / down / up on a throwaway DB (`decisionlog_test_mig126`, dropped) including a row that existed before the upgrade.
- Initial status: items produced by an extraction (`build_project_item`, used by the worker and the import script, and the email / document extractors) start `pending`. Manual items and everything that existed before are `approved`.
- Access (`app/services/access.py`): `review_visible_filter` is part of `visible_items_filter` and `item_visible`, so the review rule applies wherever the 12.4 visibility rule already did (items list, search, facets, milestones, V1 decisions list / facets / detail, project cards and detail counts, ingestion history counts, extraction version counts). `public_items_filter` (public share links) now also requires `approved`. The active-run filter (13.7) is untouched and combined as before. The digest endpoint is still a stub with no item query.
  - approved: follows the 12.4 visibility; pending: only users who reach the project through the **owning** organization (owner/admin, or assigned member), others get nothing (list, detail 404); rejected: nobody sees it unless `include_rejected=true` / `review_status=rejected` is sent, and then only the owning organization.
  - `can_review_items` = `admin` level on the project (only the owning organization's owner/admin: shared organizations never reach admin, the same rule as milestones / approving ingestion).
- API (`app/api/routes/item_reviews.py`, admin only; non-admins get 403): `POST /projects/{id}/items/{item}/review` `{status}`, `PATCH /projects/{id}/items/{item}/review` (title / statement / why / owner / due_date; first edit stores `original`, the edit approves the item), `POST .../restore-original` (puts the AI values back, clears `original`, status unchanged), `POST /projects/{id}/items/review` bulk `{status: approved|rejected, item_ids | source_id}` (by `source_id` = every pending item of that meeting's active run; only active-run, visible items of that project are touched). `GET .../items` takes `include_rejected` and `review_status`, returns `can_review`; items carry `review_status`, `reviewed_by(_name)`, `reviewed_at`, `is_edited`, and `original` (only for owning-organization users). The old `PATCH .../items/{id}` statement edit now also keeps the original (without changing review status).
- Run switching (13.7): the status lives on the item, items belong to a run; a new / re-activated run shows its own state (new extractions start pending, a rollback brings back the review of that version). Nothing is copied.
- Frontend: `ReviewStatusBadge` (Pendente / Rejeitado / Editado) on each History row, `ItemReviewPanel` in the item drilldown (approve, reject, back to pending, edit form, show AI original, restore), "Aprovar pendentes (N)" per meeting group (reviewers), "Mostrar itens rejeitados" toggle in History (reviewers); hooks in `useItemReview.ts`; pt-BR + en keys under `item:review`.
