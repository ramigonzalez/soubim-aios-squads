# Story 13.15 — On-demand Previews of Fathom Meetings Not Imported Yet

**Story ID:** 13.15
**Epic:** E13 — Recording Ingestion
**Priority:** Medium | **Effort:** 5 SP (estimate)
**Status:** Done (merged)
**Type:** Feature (migration + worker job + API + frontend)
**Requested by:** Rami — images for not-imported rows on the Fathom meetings page (`/settings/integrations/fathom`)
**Builds on:** 13.4 (download request + polling), 13.12 (`render_thumbnail`)

---

## Description

Fathom's `/meetings` list has no image, and 13.12 only thumbnails meetings that are already imported (their video is stored). For not-imported meetings the only source is the video itself. Rami chose a **per-meeting button, not automatic generation**: "Gerar prévia" asks Fathom to prepare the download (about a minute), lets ffmpeg read one frame from the signed `video.url`, and stores **only the JPEG**. The video is never stored. Previews are private to the user, because the meetings list is per Fathom account.

## Acceptance Criteria

### Data
- [x] Migration `020_story_13_15` (down_revision `019_story_13_12`): table `fathom_previews` (id, user_id FK cascade, recording_id, status queued/processing/ready/failed, thumbnail_key, download_id, job_id, error, timestamps), unique on (user_id, recording_id); up/down/up tested on a throwaway DB (dropped afterwards)

### API
- [x] `POST /api/integrations/fathom/meetings/{recording_id}/preview` (auth): invalid id → 400 (`is_valid_id`); not connected / needs reconnect → the existing 409s; storage disabled → 503
- [x] Idempotent: ready → returned with its url; queued/processing → status returned, no second job; failed → re-queued
- [x] Per-user cap: at most 3 previews queued or processing → 429 with a friendly message (an existing one in progress is still answered, not refused; the cap is per user)
- [x] Meetings list: `preview: {status, url}` per meeting (presigned GET, 6 h), only from the calling user's own previews; `null` when none
- [x] `GET /api/integrations/fathom/previews?recording_ids=a,b` (database only, max 50 ids, validated): status + url of the user's own previews, used for polling

### Worker job `fathom_preview`
- [x] Uses the user's connection: requests the download (reuses a stored `download_id`), polls with the 13.4 backoff/budget (`fathom_import.wait_for_download`), then `render_thumbnail()` on the signed `video.url`
- [x] Stores only the JPEG at `previews/user/<user_id>/fathom/<recording_id>.jpg`; never the video
- [x] Errors as in 13.4: 400/403/404/422, reconnect, disconnected user, missing storage → permanent (preview `failed`); 429/5xx, poll timeout, ffmpeg failure → retryable (3 attempts; preview goes back to `queued`, then `failed` after the last). ffmpeg failure drops the `download_id` so the retry asks for a new link
- [x] Failures are logged and never touch any Source (the job has no `source_id`)

### Reuse on import
- [x] `start_import` copies the preview's `download_id` into the new import when the preview is under 20 h old (Fathom's link lasts about 24 h); an unknown/expired id already falls back to a new download in `wait_for_download`. The 13.12 job still makes the real thumbnail after import

### Frontend
- [x] Not-imported row: placeholder plus a small "Gerar prévia" button
- [x] After the click: spinner "Gerando prévia… (~1 min)"; while any preview is queued/processing the page polls the status endpoint every 10 s (no Fathom call per poll)
- [x] Ready: the image in the same `MeetingThumbnail` atom (lazy, 16:9, falls back to the placeholder on image error)
- [x] Failed: "Tentar novamente"; 429: friendly message, button kept
- [x] pt-BR + en i18n; parity test green

## Dev Notes

- Backend: `app/services/fathom_previews.py` (request, cap, serving, worker `run`), `FathomPreview` model, `storage.fathom_preview_key()`, worker handler `fathom_preview`, routes in `app/api/routes/fathom.py`. `fathom_import._wait_for_download` became the public `wait_for_download` (duck-typed on `recording_id` / `download_id`).
- Status handling: the handler records the outcome itself (it reads the job's `attempts`/`max_attempts`). A row `queued`/`processing` for over an hour does not count toward the cap and can be requested again (lost job / dead worker).
- Frontend: `FathomMeetings.tsx` keeps a per-recording override map fed by the POST result and the polling query; `integrationsService.requestFathomPreview` / `getFathomPreviews`.
- Tests: `tests/unit/test_fathom_previews.py` (26 cases: create, idempotent, re-queue after failure, cap 429, invalid id 400, storage 503, 409s, job stores the key with fake Fathom + fake ffmpeg, poll timeout retryable, give-up after last attempt, permanent refusals, owner-only url, status endpoint, import reuse) plus 6 Vitest cases in `FathomMeetings.test.tsx`.
- No real Fathom call was made; Fathom is a `httpx.MockTransport` fake, ffmpeg and S3 are fakes.

## Assumptions & gaps (pending confirmation)

- [ ] **Per-user cap of 3 and a 429 message** were chosen to bound Fathom calls and worker time (each job can poll up to 10 minutes); confirm the number.
- [ ] **Poll budget is the import's (10 min) with 3 attempts**, so a very slow Fathom download can hold a worker for a while; a shorter budget for previews is a one-line change.
- [ ] **Previews are never deleted.** Not on disconnect, not on import, not after a retention period. The 13.1 bucket lifecycle rule covers `org/` only; a rule for the `previews/` prefix is needed (infra), and `fathom_previews` rows are removed with the user (cascade) but their objects are not.
- [ ] **The preview and the real thumbnail are separate.** After import the 13.12 thumbnail replaces the preview in the row; the preview file stays.
- [ ] **A recording id of another Fathom account** only fails inside the job (Fathom answers 404 for the user's token), so the row shows "Tentar novamente" rather than being refused at request time. The id is not checked against the user's list on the POST (that would add a Fathom call).
- [ ] **Reuse on import is best effort**: if Fathom reports the reused download `expired`/`failed`, the first import attempt fails and the retry (30 s later) asks for a new one.
- [ ] **Status endpoint polls only the page's in-progress ids**; previews started in another tab show up on the next list load.
- [ ] **One frame, no choice**, same as 13.12.
- [ ] **Fathom response shapes** (`download_id`, `video.url`) follow the 13.4 import, which was verified live; the preview job adds no new Fathom endpoint.
