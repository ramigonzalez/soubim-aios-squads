# Story 12.7 — Roles Follow-ups: Reviewer Role, Project Assignment, Admin UI Gating

**Story ID:** 12.7

## Description

Three follow-ups of the E12 role model:

1. A **`reviewer`** organization role between `member` and `admin`: reviews items (12.6) and approves / rejects / retries meetings in Ingestão, without project settings, sharing, visibility, Drive or member management.
2. A **project assignment API + UI**: organization owners/admins assign their own organization's users to the projects their organization owns or that are shared with it (members and reviewers only see assigned projects, 12.2 rule).
3. **Frontend admin gating from organization roles / per-project capabilities** instead of the legacy `user.role === 'director'`.

- [x] A reviewer cannot edit / archive the project, manage sharing, change meeting visibility, toggle milestones, create share links, delete meetings, set the Drive folder, or manage members / invitations / assignments
- [x] A reviewer without project assignment gets nothing (same as a member); a reviewer of another organization gets nothing

- [x] UI: Team page, per member / reviewer, "Projetos atribuídos: N" with a checkbox per project (shared projects marked)
- [x] Removing a member still deletes their assignments (12.5), now also on projects shared with the organization

- [x] pt-BR + en strings (parity test passes)

## Implementation Notes

- **Access levels** (`app/services/access.py`): `none < read < write < review < admin`. Owning organization: `owner`/`admin` → `admin`; assigned `reviewer` → `review`; assigned `member` → `write`. Shared organization (12.3): `owner`/`admin`, or an assigned `member` **or `reviewer`**, get the shared level (`contributor` → `write`, `viewer` → `read`), never `review`. `ASSIGNED_ROLES = ("reviewer", "member")` replaces `role == "member"` in every SQL filter (`accessible_projects_filter`, `_org_grants_access`, `review_visible_filter`), so reviewers see exactly what an assigned member sees, plus pending/rejected items of owned projects (already the 12.6 rule for the owning organization).
- `can_review_items` = level ≥ `review`; `project_capabilities()` returns `{access_level, can_review, can_manage}`.
- **Routes:** `item_reviews.py` requires `review` (was `admin`). Ingestion `PATCH /ingestion/{id}` (approve / reject), `POST /ingestion/{id}/retry` and `POST /ingestion/batch` require `review`; `DELETE /ingestion/{id}` stays `admin`. Extraction version activate / re-extract (13.7), curation upload, visibility, milestones, share links, project edit / archive / sharing stay `admin`. 403 detail for `review`: "Review access required".
- **Roles:** `ROLES = (owner, admin, reviewer, member)` (strongest first; used to order memberships). Admins manage `reviewer` like `admin` / `member` (only owners touch `owner`). `require_org_admin` is unchanged (owner/admin), so reviewers cannot list members, invite, or assign.
- **Assignment API** (`app/api/routes/organizations.py`, service in `app/services/organizations.py`), all behind `require_org_admin` (404 non-member, 403 member/reviewer):
  - `GET /api/organizations/{org}/project-assignments` → `{projects: [{id, name, owned}], assignments: [{user_id, project_id}]}`: non-archived projects owned by or shared with (contributor/viewer) the organization, and only this organization's members' assignments (a shared organization does not see the owner's assignments, and vice versa).
  - `PUT /api/organizations/{org}/members/{user}/projects/{project}` (idempotent) / `DELETE` (204, idempotent). The user must be an active member of `{org}` and the project owned by or shared with `{org}`, else 404.
  - `remove_member` now deletes the user's assignments on projects owned by **or shared with** the organization (was: owned only).
- **Migration `017_story_12_7`:** drops / recreates the two role CHECK constraints with `reviewer`. Downgrade turns reviewers into members first. Verified upgrade 016 → head, downgrade to 016 with a reviewer row (became `member`, old constraint back), upgrade head again (row can be set to `reviewer`) on throwaway `decisionlog_test_mig127` in `decision-log-backend-db-1` (dropped afterwards).
- **Frontend:** `useActiveOrganization().canReviewSomewhere` (owner/admin/reviewer in any organization) gates the Navigation ingestion link and the Ingestion page; ingestion row actions follow each source's `can_review` (approve / reject / retry, select-all only reviewable rows) and `can_manage` (delete). `ProjectDetail` uses `can_manage` (edit, archive, share/export toolbar, milestone star) and `can_review` from the items response. Team page: `reviewer` in the role selectors (invite + members) and a per-member project assignment panel (`useProjectAssignments` / `useSetProjectAssignment` in `useTeam.ts`). Types: `OrganizationRole` + `reviewer`, `ProjectCapabilities`, `OrganizationProjectAssignments`, ingestion `can_review` / `can_manage`.

## Security review

@architect, 2026-10-06, on the uncommitted 12.7 changes (worktree `feature/12.7-roles-followups`).

**Access levels.** Every route that calls `require_project_access` / `require_source_access` / `has_access` was enumerated. `_RANK` keeps `review` (3) strictly between `write` (2) and `admin` (4), and no route compares levels with `==` except `== NONE`, so:
- routes that required `write` now also accept a reviewer: items create / patch, decisions patch, stages, participants, documents, uploads, the transcript webhook, Fathom imports. This is assumption 2.
- routes that require `admin` stay closed to reviewers: project patch (including the Drive folder) and archive, `project_organizations` (sharing), share links, the milestone toggle, `DELETE /ingestion/{id}`, extraction-run activate and re-extract, curation upload.
- visibility and shared-at-creation (`can_change_visibility`, `can_create_shared`) check `ADMIN_ROLES` directly, so reviewers are excluded.
- members, invitations and assignments sit behind `require_org_admin` (owner/admin).
- `review` is granted only for the owning organization (`project_access_by_organization`). A shared organization's reviewer gets the shared level, and an unassigned reviewer, or a reviewer of another organization, gets `none`.
- capability fields (`access_level`, `can_review`, `can_manage`) come from `project_access_level`, the same function the routes enforce.

**Migration `017_story_12_7`:** tested on the throwaway `decisionlog_test_rev127`, which was dropped afterwards.
- at 016, `reviewer` is rejected.
- upgrade to head, then a `reviewer` member and a `reviewer` invitation are accepted, and an unknown role is still rejected.
- downgrade to 016: both rows became `member` and the old constraint is back.
- upgrade to head again: OK.

**Invitations:** `reviewer` can be invited. `create_invitation` still goes through `can_manage_role`, so only owners grant `owner` (12.5), and reviewers cannot invite (403).
