# Story 13.14 — Extraction Model Choice Explained to Users, Plus Eval

**Story ID:** 13.14
**Epic:** E13 — Recording Ingestion
**Priority:** Medium | **Effort:** 5–8 SP (estimate) + eval time
**Status:** Draft
**Type:** Feature (UX, configuration) + evaluation plan
**Requested by:** Rami — default **Opus** (yes). "We need to explain to the user how that affects the result. We didn't define our pricing model. The value is extracting valuable data from meetings, but depending on context Sonnet can perform better on documents and email threads."

---

## Story

As an **organization admin**, I want to choose the model for an extraction and understand in plain language what that choice changes (quality, speed, cost), so that I can pick the right trade-off per meeting, document or email thread.

## Context (current behaviour and facts, verified)

- **One global model.** `settings.llm_model = "claude-opus-5-5"` (`app/config.py`), used by `app/services/extraction_v2.py` (`model=settings.llm_model`, effort `settings.extraction_effort`, `extraction_max_tokens`). No per-run, per-organization or per-source-type choice.
- **Re-extract.** `POST /api/sources/{id}/re-extract` (`app/api/routes/extraction_runs.py`, project admin) takes **no body**: it enqueues `process_source` with `re_extract: true` and the worker uses the global model. The button is "Extrair novamente" (`meeting.json` key `reExtract`). Each run stores `ExtractionRun.model`, `prompt_version`, tokens (13.7).
- **Cost.** 13.6 shows an estimated cost per version from list prices in `MODEL_PRICING` (`app/config.py`): Opus 5.5 **$4 in / $20 out** and Sonnet 5.5 **$2 in / $10 out** per MTok; ignores cache and batch discounts (13.6 Assumption 2).
- **Measured for meetings only** — D/SEASON eval, `data/eval/dseason-2026-09-04/` (`comparison.md`, `run_models.sh`, `compare.py`, same prompt and schema for all models):
  - Opus 5.5: **most complete (28 items)**, 126 s, 15.9k output tokens.
  - Sonnet 5.5: **fastest (49 s)**, complete (20 items, all decisions with why/consensus/impacts, all action items with owner), 8.0k output tokens.
  - Haiku 4.5: 15 items, 189 s, 17.9k output tokens (not a candidate).
  - Agreement between models is partial (e.g. 10 of Sonnet's 20 items have a similar item in Opus), which is the same non-determinism seen in 13.13.
  - All three runs exceeded the 4096-output limit of the production setting in that eval (flagged "truncated" in the report); check `extraction_max_tokens` before comparing production runs.
- **Documents and email threads are not measured yet.** Their extraction paths are `app/services/document_extractor.py` and `email_extractor.py`; they are not versioned (13.7 Assumption 4) and use the same global model. Rami's hypothesis (Sonnet may do as well or better on documents/emails) is untested.
- **Pricing model for customers is undefined.** This story shows estimated model cost but does not define what users are charged.

## Acceptance Criteria (draft) — phase 1

### A. Model choice in "Extrair novamente"
- [ ] `POST /api/sources/{id}/re-extract` accepts optional `{ "model": "claude-opus-5-5" | "claude-sonnet-5-5" }` (allow-list from `MODEL_PRICING`, anything else 422). Omitted → the default for the source type (B). The worker payload carries `model`; `ExtractionRun.model` stores what was used (already a column).
- [ ] The re-extract UI becomes a small dialog: model picker (default preselected), a plain-language explanation, and the **estimated cost before running** (see C), a confirm button. The explanation in pt-BR and en (draft wording, to approve by Rami):
  - **Opus** — "Mais completo. Costuma encontrar mais decisões e ações, em especial em reuniões longas. Mais lento e mais caro."
  - **Sonnet** — "Mais rápido e mais barato. Resultado completo na maioria das reuniões, com menos itens de detalhe. Pode ser melhor em documentos e e-mails." (the last sentence only after the eval confirms it)
  - A note that **results can differ between runs and between models**; every run is kept as a version (13.7) and can be compared or restored.
- [ ] The first import (13.4/13.5 and webhook 13.9) uses the default model; no dialog.
- [ ] Only project admins can choose (as re-extract today, 12.7 keeps reviewers out).

### B. Per-source-type default model
- [ ] Setting `extraction_default_models`: `{ meeting, document, email }` → model id. Defaults: `meeting` = Opus (Rami's decision), `document` and `email` = Opus until the eval says otherwise. Phase 1 stores it in config/env (`app/config.py`, like `MODEL_PRICING`); a DB or per-organization setting is phase 2. `extraction_v2.py` and the document/email extractors read it instead of `settings.llm_model`.
- [ ] Changing a default never re-runs existing extractions.

### C. Estimated cost before running
- [ ] `GET /api/sources/{id}/extraction-estimate?model=...`: estimated input tokens (transcript/text length ÷ ~4 chars per token plus prompt size) and output tokens (from the previous run of the same source if any, else the average of this source type), times list price. Shown as a range ("~US$0,35 a US$0,60 (estimativa)"), explicitly list price, no cache/batch discount.
- [ ] Reuse `MODEL_PRICING` and the 13.6 cost formatter. Models missing from the table show "custo indisponível", not zero.
- [ ] Show the same estimate next to the cost already displayed per version (13.6) so users can compare runs.
- [ ] The estimate is visible to the roles allowed to run the extraction, not to every viewer (open question: 13.6 Assumption 3 shows cost to everyone).

### D. Eval plan for documents and email threads (deliverable: a plan + a script, not a spend)
- [ ] A written eval plan in `data/eval/` (or `docs/qa/`): 
  - **Dataset:** N real documents (project documents of different kinds: specs, memos, contracts, drawings lists) and N real email threads from D/SEASON and one other project, anonymized if they leave the repo. Proposal: 10 documents + 10 threads, 3 languages mix (pt-BR, en).
  - **Method:** same as the meeting eval: same rendered prompt and schema per model, models Opus 5.5 and Sonnet 5.5 (Haiku only if Rami wants), reuse `run_models.sh` / `compare.py`.
  - **Grading:** a rubric per item type (recall of decisions and action items against a human-made list, precision, owner/date correctness, hallucination count, why/consensus quality), blind pairwise preference by one reviewer, plus automatic metrics (item counts, agreement, latency, tokens, cost).
  - **Cost estimate:** tokens × list price for the dataset and both models, with a total, written in the plan.
  - **Decision rule:** what difference changes the default (e.g. Sonnet is the default for a type if recall ≥ 95% of Opus and its cost is half).
- [ ] **Needs Rami's approval before any spend.** Do not run the eval until the plan and the estimated cost are approved.

## Dev Notes

- **Affected backend:** `app/api/routes/extraction_runs.py` (body, validation, estimate route), `app/services/extraction_v2.py` (take `model` as a parameter), `document_extractor.py`, `email_extractor.py`, `app/worker.py` (pass `model` from the payload, 13.7 already passes `re_extract`), `app/config.py` (`extraction_default_models`, `MODEL_PRICING`), `app/services/jobs.py` payload.
- **Affected frontend:** the re-extract control in the extraction versions panel (13.7, `meeting.json` `reExtract`), a new `ReExtractDialog` organism, i18n (`meeting`), types.
- **No migration** (model stored on `ExtractionRun` already). A migration only appears with phase 2 org-level defaults.
- **Fallbacks.** `extraction_v2.py` sends `"fallbacks": "default"`; the run should store the model actually used, not only the requested one. Verify.
- **Effort/limits:** compare under the same `extraction_effort` and `extraction_max_tokens`; the D/SEASON eval ran through the CLI without the 4096 limit.
- **Transparency.** Do not claim Sonnet is better for documents in the UI until the eval supports it (the draft sentence above is conditional).
- **Risks:** estimates may be off by a factor of two (output tokens, thinking); label them "estimativa". Prices change: keep `MODEL_PRICING` the single source and show the date of the prices.

## Out of scope (phase 2)

- A pricing model for customers (plans, credits, markup). Estimated model cost is informational only.
- Per-organization or per-project default model in the database and a settings screen.
- Automatic model routing by length/type, or "try both and pick".
- Side-by-side diff of two versions (13.7 gap), and a model/cost comparison table across versions.
- Running the document/email eval itself (needs approval), and any change of the defaults before its results.
- Batch/caching discounts in the estimate; Haiku as a user-selectable option.
