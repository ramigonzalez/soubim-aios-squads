# Story 13.4 — Browse & Import Fathom Meetings

**Story ID:** 13.4
**Epic:** E13 — Recording Ingestion
**Priority:** High | **Effort:** 8 SP (estimate)
**Status:** Ready for Review
**Type:** Feature
**Requested by:** Rami — "visualize Fathom's recordings and request those recordings from the app"

---

## Description

A connected user browses their Fathom meetings in DecisionLog and **picks** which to import into a project. The import job downloads the recording by `recording_id` into storage and stores Fathom's transcript; the meeting then appears in Ingestão as pending, ready for extraction.

## Acceptance Criteria

- [x] "Reuniões do Fathom" page: list of the connected account's meetings (title, date, duration, invitees), paginated, searchable; already-imported ones marked — search filters the pages loaded so far (see Assumptions)
- [x] Import dialog: target project (projects the user's organization can contribute to)
- [ ] Import dialog: visibility (internal default / shared) — **deferred: Story 12.4 is not implemented yet** (no `sources.visibility`); see Assumptions
- [x] `fathom_import` job (13.2): `POST /recordings/{id}/download` → poll download status → stream the MP4 into storage (13.1, no local file) → create Source (`source_type=meeting`, title, occurred_at, duration, participants from invitees, `recording_id`, transcript in our `M:SS - Name` format as `raw_content`) — `recording_id` is kept on the `fathom_imports` row linked 1:1 to the Source (see Assumptions)
- [x] Idempotent: importing the same `recording_id` twice into a project is refused
- [x] Nothing is imported automatically
- [x] Errors visible on the meeting (expired link, `failed` download, 422 no media) with retry

## Dev Notes

- **Proven by spike:** list returns `recording_id`, `title`/`meeting_title`, `recording_start_time`, `calendar_invitees`, `recorded_by`, `transcript`, `share_url`, `next_cursor`; download: `POST /recordings/{id}/download` → `202 processing` → `GET /recordings/{id}/downloads/{download_id}` → `completed` with a signed `video` URL valid ~24 h (26 s test video ready in ~15 s; long meetings will take longer — the job polls).
- The connected account's list mixes personal and work meetings (interviews, other clients) — reason for explicit picking, and for not showing one user's Fathom list to others.
- A user only sees recordings their Fathom account can access: D/SEASON wasn't in the owner's list because another account recorded it.
- Fathom's transcript has speakers per microphone (shared room mics merge people) — E14 fixes attribution.

## Implementation

```
Browse page ──GET /meetings──▶ API ──FathomClient (user's own token)──▶ Fathom list
Import dialog ─POST /imports─▶ API: write access? duplicate? → fathom_imports row + fathom_import job
worker: find meeting in importer's list (with transcript) → POST download → poll → stream MP4 → storage
        → Source(id = import id, meeting, pending, transcript M:SS) → shows in Ingestão
```

- **Table** `fathom_imports` (migration `010_story_13_4`, down_revision `009_story_13_3`): `id` (also the Source id, so the storage key is known before the Source exists), `project_id` (FK, cascade), `recording_id`, `user_id` (importer, SET NULL), `source_id` (FK sources, **cascade**, unique), `job_id` (FK jobs, SET NULL), `download_id` (reused across retries), timestamps; **unique `(project_id, recording_id)`** = idempotency. Status is derived: `source_id` set → imported (then the Source's ingestion status), otherwise the job's status (queued / running / failed).
- **Routes** (`app/api/routes/fathom.py`, all authenticated):
  - `GET /api/integrations/fathom/meetings?cursor=` → one page of the **current user's own** Fathom list (no transcripts), normalized (`recording_id`, `title`, `started_at` UTC, `duration_minutes`, `invitees`, `recorded_by`, `share_url`) + `imports` of that recording into projects the user can see. 409 `not_connected` / `needs_reconnect`, 502 when Fathom fails.
  - `GET /api/integrations/fathom/projects` → non-archived projects with **write** access (12.2: org admins → all org projects; members → assigned projects).
  - `POST /api/integrations/fathom/imports {recording_id, project_id}` → 202 + import. Write access required (404/403); `recording_id` validated (`[A-Za-z0-9_-]{1,128}`); 409 `already_imported` (with the existing import); 503 when storage is not configured; 409 when Fathom is not connected.
  - `POST /api/integrations/fathom/imports/{id}/retry` → only failed imports (409 otherwise), only by the importer (403; the recording is in their Fathom account), 404 if the project is not visible.
- **Job** (`app/services/fathom_import.py`, handler `fathom_import` in `app/worker.py`, `max_attempts=5`):
  1. finds the recording in the importer's list with `include_transcript=true` (follows the cursor, up to 30 pages) — a recording the importer's account cannot see fails permanently;
  2. reuses a stored `download_id` or `POST /recordings/{id}/download`, then polls every 5 s for up to 10 min (then retries later, keeping the id);
  3. streams the signed video URL into `org/<project owner org>/sources/<import id>/recording.mp4` (`storage.put_stream_from_url`, size guard);
  4. creates the Source: `meeting`, `pending`, `included=false`, `source_label="Fathom"`, title, `occurred_at` (recording start, UTC), duration (end − start), participants (`calendar_invitees`, else the recorder), `recording_url` = share URL, `raw_content` = transcript as `M:SS - Name` + indented text (`H:MM:SS` from one hour — what `lib/transcript.ts` parses and extraction reads).
  - Permanent (fail at once): 422 no media, 400/403/404 from Fathom, recording not in the account, reconnect needed, importer disconnected, too large, Fathom/storage not configured on the worker. Retried with backoff: 429/5xx/network, download `failed` / `expired` (download id cleared → a new one is requested), signed link 403/404/410 (expired), still processing after 10 min.
  - Does **not** enqueue `process_source`: the meeting waits in Ingestão for approval like any other source (AC "nothing is imported automatically"; extraction starts on approve).
- **Concurrent refresh (open item from 13.3, fixed)**: `FathomClient.refresh` locks the connection row (`SELECT … FOR UPDATE`, re-read with `populate_existing`) for the whole refresh; after acquiring the lock, if the access token differs from the one the caller used and is not about to expire, another process already refreshed → use it, no call to Fathom. The 401-retry path passes the token it used. PostgreSQL test with two sessions/threads: one refresh call, both get the new token, connection not marked needs-reconnect.
- **Frontend**: page `/settings/integrations/fathom` ("Reuniões do Fathom", linked from the connected Fathom card in Integrações): cursor pagination ("Carregar mais"), search box, per meeting the date/time, duration, invitee count and names, and its imports — "Importada em <projeto>" + `IngestionStatusBadge` with the meeting status; "Importando para <projeto>" + the worker badge (Na fila / Processando / Nova tentativa n/m); "Falha ao importar" + error + "Tentar novamente" (importer only). Polls every 5 s while an import is with the worker. `FathomImportDialog` (organism, Radix Dialog): project select (already-imported projects disabled), specific messages for 409 / 503. i18n keys under `integrations.meetings.*` (pt-BR + en) and `integrations.fathom.browse`.

## Assumptions & gaps

Each item: chosen option — alternatives — who should confirm.

1. **Visibility not offered (12.4 not implemented)** — the dialog only picks the project; imported meetings behave like every other source today (visible to everyone with access to the project). When 12.4 lands it adds `owner_organization_id`/`visibility` to `sources`; the import then sets owner = importer's active organization and `internal` by default (12.4 Dev Notes) — one field in the dialog + two in `fathom_import._run`. Alternative: block 13.4 until 12.4. — **Rami**.
2. **`recording_id` lives on `fathom_imports`, not on `sources`** — the import row is 1:1 with the Source (same id, `source_id` FK) and carries the unique `(project_id, recording_id)`; it also holds the job/download state needed for status and retry before any Source exists. 13.9 (webhook auto-import) can create the same rows. Alternative: `sources.external_id` + a unique index (needs a separate place for in-flight state anyway). — **@architect**.
3. **Duplicate rule** — refused while an import row exists for (project, recording): queued, running, failed (retry instead) or imported, even if the meeting was rejected in Ingestão. Deleting the meeting in Ingestão deletes the row (FK cascade), so it can be imported again. Alternative: allow re-import after reject. — **@po**.
4. **Write access to import** (12.2 levels: org admins/owners, assigned members) — the story says "projects the user's organization can contribute to". When 12.3 adds shared projects, `project_access_level` decides whether a partner org can write. — **Rami**.
5. **Search is client-side over loaded pages** — Fathom's list API has no text search (spike); "Carregar mais" extends what the search covers (hint under the box). Alternative: server-side scan of N pages per search (slow, rate-limited). — **@po**.
6. **Metadata and transcript come from the list endpoint** (`include_transcript=true`, scanning up to 30 pages for the recording) — the only shape proven by the spike; also guarantees the importer's own Fathom account can see the recording. Recordings older than ~30 pages fail with "not found". Alternative: `GET /recordings/{id}/transcript` (documented by Fathom, not tested in the spike) + metadata from the browse page. — **Rami** (check live with an old meeting).
7. **Retry only by the importer** — the job runs with the importer's Fathom token. Another writer can import the same recording into another project with their own account, but not take over someone's failed import. — **Rami**.
8. **Download wait**: poll 5 s, 10 min budget per attempt, 5 attempts with the queue's backoff (30 s, 60 s, 120 s, 240 s) ≈ 50+ min in total before the import is marked failed (then manual retry, which reuses a still-valid download id). Long (98 min) meetings were not measured. — **Rami** (live test).
9. **Storage is required** — import returns 503 when `S3_*` are not set (no local-disk fallback for imports); the worker fails permanently with the same reason. Alternative: import transcript only and keep the Fathom share URL as an external recording. — **Rami**.
10. **Errors shown as text from the job** (`last_error`, English) next to a localized "Falha ao importar" title. Alternative: error codes mapped to pt-BR messages. — **@ux-design-expert** (low stakes).
11. **Transcript turns are 1:1 with Fathom segments** (no merging of consecutive segments of the same speaker) — keeps timestamps fine-grained for the viewer's seek. — **@po**.
12. **Page location** — `/settings/integrations/fathom`, reached from the connected Fathom card in Integrações (no navigation-bar entry). Alternative: a link in Ingestão or the navigation bar. — **UX/Rami**.
13. **Gap — not verified against the real Fathom API**: field names of the download status (`video.url` or a `video` string — both handled) and of transcript segments (`speaker.display_name`, `text`, `timestamp` "HH:MM:SS") follow the spike notes and Fathom's public docs; all tests use `httpx.MockTransport`. Confirm with the live test below.

### Live test (Rami)

Prerequisites: 13.3 live test done (Fathom connected), SeaweedFS from 13.1.

1. `decision-log-backend/.env`: `FATHOM_CLIENT_ID`, `FATHOM_CLIENT_SECRET`, `FATHOM_REDIRECT_URI=https://naturally-ethical-shark.ngrok-free.app/api/fathom/callback`, `TOKEN_ENCRYPTION_KEY` (same as before — a new key forces reconnect), and `S3_ENDPOINT=http://127.0.0.1:9000`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_BUCKET` (13.1 "Local dev setup"). The worker reads the same `.env`.
2. `cd decision-log-backend && docker compose up -d storage && venv/bin/alembic upgrade head` (applies `010_story_13_4`).
3. `./dev.sh` (API + **worker** + frontend) and `ngrok http --url=naturally-ethical-shark.ngrok-free.app 8000` (needed only for (re)connecting; browsing/importing calls Fathom from the backend).
4. Integrações → **Ver reuniões do Fathom**: your meetings appear (title, date, duration, invitees); "Carregar mais" loads older ones.
5. **Importar** a short meeting → pick a project → the row shows "Importando para … · Na fila/Processando"; the worker log shows the job; after the download it shows "Importada em … · pendente".
6. Ingestão: the meeting is pending (source "Fathom"); open it in the meeting viewer — video plays from storage with seeking and the transcript turns line up. Approve → extraction runs as before.
7. Import the same meeting into the same project again → "Esta reunião já foi importada neste projeto."
8. Worth checking: a long meeting (download preparation time), an old meeting (> 30 list pages back), and a recording without video (expect "no media" + "Tentar novamente").
