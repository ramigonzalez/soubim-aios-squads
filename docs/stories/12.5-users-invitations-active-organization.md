# Story 12.5 — Users, Invitations & Active Organization

**Story ID:** 12.5
**Epic:** E12 — Organizations & Client Access
**Priority:** High | **Effort:** 5 SP (estimate)
**Status:** Ready for Review
**Type:** Feature
**Requested by:** Rami — grant clients access through the app

---

## Description

Organization admins invite people by email; invitees create their account (or log in) and join the organization. Users in more than one organization switch the **active organization** in the navigation; everything they see is scoped to it (12.2).

## Acceptance Criteria

- [x] `organization_invitations`: email, organization, role, token (hashed), expires_at, accepted_at (+ `revoked_at`, `organization_name`, `invited_by`) — migration `012_story_12_5`
- [x] Admin UI: invite by email with role, list pending invitations, revoke — Settings → Team (`/settings/team`), which also lists members, changes roles and removes members
- [x] Accept flow: invitation link (`/invite/:token`) → set name + password (new user, logged in right away) or log in (existing) → membership created
- [x] Inviting a company that has no organization yet: platform admins invite with a company name; the organization is created on acceptance and the invitee becomes its `owner`
- [x] Organization switcher in Navigation; active organization stored client-side and sent as `X-Organization-Id` with every API call
- [x] Email sending: pluggable `EmailSender` interface; in dev the link is printed in the backend log. No provider chosen (open decision) — see Assumptions

## API (implemented)

| Endpoint | Who | Notes |
|----------|-----|-------|
| `POST /api/invitations` `{email, role, organization_id}` | owner/admin of the organization | 201 with `invite_url` (shown once); a new invitation for the same email + organization revokes the previous; 409 if already a member; only an owner can invite as `owner` |
| `POST /api/invitations` `{email, organization_name}` | platform admin (owner/admin of souBIM) | new company: role is always `owner`; organization created on acceptance |
| `GET /api/organizations/{id}/invitations` | owner/admin | pending only (no link) |
| `DELETE /api/invitations/{id}` | owner/admin of its organization | revoke |
| `POST /api/invitations/public/preview` `{token}` | public | organization, email, role, `account_exists`; 404 unknown, 410 used/revoked/expired |
| `POST /api/invitations/public/accept` `{token, name, password}` | public | new user only (409 if the email has an account: log in instead); returns a login token |
| `POST /api/invitations/accept` `{token}` | logged-in user | the account email must equal the invited email (403 otherwise) |
| `GET /api/organizations/{id}/members` | owner/admin | |
| `PATCH /api/organizations/{id}/members/{user_id}` `{role}` | owner/admin | admins cannot touch/grant `owner`; the last owner cannot be demoted (409) |
| `DELETE /api/organizations/{id}/members/{user_id}` | owner/admin | the last owner cannot be removed (409); also removes the member's assignments to the organization's projects |
| Any authenticated endpoint + header `X-Organization-Id` | member of that organization | 403 otherwise (checked in the auth middleware); `/api/organizations/me` ignores the header so a stale id cannot lock the client out |

## Assumptions & gaps

Each item: chosen option — alternatives — who should confirm.

1. **Token**: 256-bit random (`secrets.token_urlsafe(32)`), stored as SHA-256 (high-entropy token: no slow hash needed), expires after 7 days (`INVITATION_EXPIRE_DAYS`), single use (`accepted_at`), revocable (`revoked_at`). Link: `{FRONTEND_URL}/invite/{token}`. — Alt: shorter expiry, bcrypt-hashed token. — **Rami**.
2. **Email provider not chosen**: `app/services/email_sender.py` defines `EmailSender`; the default `LogEmailSender` prints the message (with the link) only when `ENVIRONMENT` is `development`/`test`; in any other environment it logs "not sent" without the link. Since nothing is delivered, the create response returns `invite_url` once to the inviting admin, who sends it (this is how the **first production users** get in: a souBIM admin invites them; the very first souBIM owner still needs to exist, see gap 9). — Alt: return no link and require a provider before going live (Resend / Postmark / SES). — **Rami** (provider, cost).
3. **Existing email = log in, never takeover**: the public accept endpoint refuses (409) an email that already has an account; the invitee logs in and uses the authenticated accept, which requires the same email (case-insensitive). Wrong email gives 403. — Alt: allow accepting with a different account. — **@architect**.
4. **New users get `users.role = 'client'`** (legacy column, not used for authorization since 12.2) and a password of at least 8 characters (the app has no password policy yet). — **Rami**.
5. **Roles**: owner and admin can invite/manage; **only an owner can grant, change or remove `owner`**; admins manage `admin`/`member`. An organization always keeps at least one owner. — Alt: admins manage everything except the last owner. — **Rami**.
6. **New company invitations** are limited to platform admins (owner/admin of the `soubim` organization, same rule as 12.2 platform endpoints); the frontend shows the option only when the active organization has slug `soubim`. The invitee always becomes `owner`. Organization slug is derived from the name (`new-co`, `new-co-2`...). — Alt: any organization admin may create companies. — **Rami**.
7. **Active organization = request header `X-Organization-Id`** (stored in `localStorage` + zustand `organizationStore`, sent by the axios client), validated for **every** authenticated request in the auth middleware (non-member or malformed id gives 403). Scoping: `GET /api/projects` returns only projects **owned by or shared with** the active organization (12.3), intersected with the user's access. **Without the header the behaviour is unchanged (union of the user's organizations, 12.2)**, so existing clients and API users keep working. `app/services/access.py` was not touched (parallel 12.4 work). — Alt: token claim (needs re-login to switch); making `access.py` active-org aware so detail routes, ingestion, digest... are also scoped. — **Rami / @architect**.
8. **Gap — scoping is only the project list**. Detail/ingestion/history/digest routes still authorize by the union of the user's organizations (a user who knows a project id of another of their organizations can open it while another is active), and `GET /auth/me` / login `projects` ids are not narrowed. Nothing leaks between users; it is a consistency gap. Next step: pass the active organization into `access.py` (after 12.4 lands). — **Rami / @architect**.
9. **Gap — first production user / seed**: demo users are already not seeded outside demo mode (`init_db` guard, 7.18); an initial souBIM owner has no creation path in the app (needs a one-off script or DB insert). Not built (scope).
10. **Gap — project assignment for `member`s**: members only see projects they are assigned to (12.2) and the story does not ask for an assignment API/UI, so none was built. Until then, invite people who should see everything as `admin`; a `member` sees nothing. Needs a decision: assignment API + UI, or "members see all projects of the organization" (12.2 assumption 1). — **Rami** (high priority: affects every invited client).
11. **Gap — frontend admin gating** (12.2 gap 10) is not changed: `Navigation` ingestion link, `Ingestion` page and `ProjectDetail` still use `user.role === 'director'`. Only the new Team link / page use organization roles (`/api/organizations/me` of the active organization). — **Rami**.
12. **Gap — no "forgot password"**, no resend button (inviting again revokes the old link and creates a new one), no history view of expired/accepted invitations, no rate limit on the public invitation endpoints (256-bit tokens). — follow-ups.
13. Removing a member does not revoke their JWT (stateless, 7 days); access disappears immediately because authorization reads memberships on each request.

## Security review

Scope: `git diff origin/main...HEAD` (public invitation endpoints, invite creation / members, `X-Organization-Id`, token exposure, login `?redirect=`, rate limiting).

| # | Finding | Severity | Status |
|---|---------|----------|--------|
| 1 | **Open redirect after login**: `?redirect=` accepted any value starting with `/` and not `//`, so `/\evil.com` (browsers read `\` as `/`) and `/<TAB>/evil.com` (the URL parser strips tabs/newlines) left the site; react-router falls back to `location.assign` when `pushState` refuses a cross-origin URL. | High | **Fixed**: `src/lib/safeRedirect.ts` (single leading `/`, no `//` or `/\`, no backslash / control / whitespace characters, resolved origin must equal the page origin, else `/projects`); unit + Login tests. |
| 2 | **Single use not atomic**: accept checked the invitation, then wrote `accepted_at` at the end. Two concurrent accepts (or an accept racing a revoke) could both pass the check: a new-company invitation could create two organizations, a revoked link could still be used. | Medium | **Fixed**: `_claim` takes the invitation with a conditional `UPDATE ... WHERE accepted_at IS NULL AND revoked_at IS NULL AND expires_at > now` before creating the user / organization / membership; 0 rows → rollback + 410. Tests simulate a revoke / accept between lookup and use. |
| 3 | **Last-owner protection race**: two owners demoting / removing each other at the same time both counted 2 owners → organization without owner. | Medium | **Fixed**: owner rows locked (`SELECT ... FOR UPDATE`) before roles are read in `change_member_role` / `remove_member`; threaded PostgreSQL test (one gets 403, one owner left). |
| 4 | Public accept returned **500** for: a password over 72 bytes (bcrypt 5 raises), a name or company name over 255 chars, an email held by a soft-deleted account (`users.email` unique). | Low | **Fixed**: 422 / 409; the length checks run before the invitation is taken, so it stays usable. Concurrent registration of the same email → 409. |
| 5 | Invite link logged when `ENVIRONMENT` is `development`/`test`, and `development` is the **default** of `settings.environment`: a deployment that forgets `ENVIRONMENT=production` logs live invite links. | Medium | Open — make sure every deployed environment sets `ENVIRONMENT`; consider failing startup when `ENVIRONMENT` is unset outside local. |
| 6 | **No rate limit** on `/api/invitations/public/*` (the in-memory limiter is only on login). Guessing a 256-bit token is infeasible; the main cost is bcrypt CPU on accept, which needs a valid token. | Low | Fixed in Story 13.11 (per IP, shared storage via Redis when configured). |
| 7 | New-company invitations (`organization_id` NULL) cannot be revoked (`DELETE /api/invitations/{id}` → 404) or listed; only re-inviting the same email + name revokes them. | Low | Open — platform-admin list/revoke follow-up. |
| 8 | Pending invitations stay valid after the inviter is demoted or removed. | Low | Open — accepted risk (an admin can revoke them). |
| 9 | Token in the URL path (`/invite/{token}`): browser history and `Referer` (modern browsers send origin only cross-site by default). | Low | Open — optional `Referrer-Policy: no-referrer` on the frontend host. |
| 10 | Login compares email case-sensitively, invitations store it lowercased: an invitee typing `New@X.com` at login fails. Pre-existing login behaviour. | Low | Open — normalize email in login (functional). |
| 11 | Production log line "message to {email} was not sent" contains the recipient email (PII). | Low | Open. |

Verified OK (no change): token = `secrets.token_urlsafe(32)` (256 bits), only SHA-256 stored, looked up by hash (no secret compared in app code, timing leaks nothing usable); expiry, revoke and single use enforced on preview and accept; preview reveals org name, invited email, role and `account_exists` to the token holder only; the email, role and organization come from the invitation, never from the request body (extra fields ignored, test); existing email → 409 on the public endpoint, authenticated accept requires the same email (case-insensitive) and never changes an existing membership role; only owner/admin of the organization can invite / list / revoke / manage, admins cannot grant, change or remove `owner`; cross-organization ids → 404 (members and invitations are always filtered by the organization in the path / of the invitation); new-company invitations checked by `is_platform_admin` on the backend (slug `soubim`; a new company named "souBIM" gets slug `soubim-2`); `X-Organization-Id` validated by the middleware on every authenticated request (malformed / non-member → 403, never 500), only ANDs a filter on the project list, `/api/organizations/me` exemption only lists the caller's own memberships; `invite_url` only in the create response, never in lists or previews.
