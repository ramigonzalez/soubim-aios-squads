# Story 13.13 — Fathom Import per Organization (One Copy per Organization)

**Story ID:** 13.13
**Epic:** E13 — Recording Ingestion
**Priority:** Medium | **Effort:** 5–8 SP (estimate)
**Status:** Draft
**Type:** Feature (data model, security)
**Requested by:** Rami — "A Fathom meeting can be imported by souBIM AND by DIMAS. The same meeting can generate non-deterministic results. Open question, needs thinking."

---

## Story

As an **organization admin or importer**, I want to import a Fathom recording into a project even if another organization on that project already imported it, so that each organization has its own copy, extraction and visibility.

## Context (current behaviour, verified)

- `fathom_imports` has `UniqueConstraint("project_id", "recording_id", name="uq_fathom_imports_project_recording")` (`app/database/models.py`, 13.4). One import per (project, recording) **across all organizations**.
- If souBIM imports a recording, DIMAS gets **409 `already_imported`** from `POST /api/integrations/fathom/imports` (`import: null` when the existing import is not visible to DIMAS, the 12.4 fix). The 409 still reveals that *some* organization imported it: 12.4 Security finding 4, **open** ("decide per-organization uniqueness `(project, recording, owner_organization)`").
- Each import creates one Source with `owner_organization_id` = the importer's acting organization and the chosen visibility. The Source id equals the import id. The video goes to `org/<org_id>/sources/<source_id>/recording.<ext>` where `<org_id>` is **the project owner's organization**, not the source owner's (`org_id_for_source` in `app/services/recordings.py`, `recording_key` in `app/services/storage.py`; 12.4 Assumption 8).
- Extraction and versions are per Source (13.6, 13.7: `ExtractionRun`, `re-extract`, activate).
- The recordings a user can import come from the user's **own** Fathom account (13.3/13.4), so one meeting can appear in two organizations' accounts.

## The open question: what is "the same meeting" in DecisionLog?

LLM extraction is not deterministic, and the organizations may use different models or settings (13.14). Two copies produce **different items** (wording, sometimes counts).

| Option | Description | Pros | Cons |
|--------|-------------|------|------|
| **(a) Separate copies** (recommended phase 1) | One import, Source, recording copy, extraction and visibility **per organization**. Unique `(project, recording, organization)` | Simple; reuses 12.4 ownership and 13.7 versions unchanged; no cross-org coupling; each organization controls delete/visibility; closes 12.4 finding 4 | Video stored twice; extraction cost twice; two near-identical meetings in History if both are shared (handled by the grouping below); items of the copies can disagree |
| **(b) One canonical meeting, per-org extraction versions** | One Source and recording; each organization adds its own `ExtractionRun` and sees its own items | One video and transcript; natural "same meeting" identity | Large change: 12.4 visibility is per Source, so per-org items need a new access model; delete/ownership become ambiguous; the canonical meeting's existence can reveal a private one; high risk |
| **(c) Keep one import** (today) | First importer wins | Nothing to build | DIMAS blocked by a 409 that leaks existence; the first importer's visibility choice decides for everyone; contradicts "each client imports their own Fathom meetings" (13.4) |

**Recommendation: (a)** now; (b) only if users ask for one merged result. Record the decision in this story before development.

## Acceptance Criteria (draft)

- [ ] Replace `uq_fathom_imports_project_recording` with a unique `(project_id, recording_id, owner_organization_id)`. Migration: next free number after 018. No data backfill (`owner_organization_id` is already NOT NULL).
- [ ] `POST /api/integrations/fathom/imports`: the duplicate check is scoped to the importer's acting organization. An import by **another** organization succeeds with its own import row, Source, extraction and visibility. A duplicate within the **same** organization is still 409 `already_imported` (it is the caller's own, so no leak).
- [ ] `GET /api/integrations/fathom/meetings`: shows the caller's organization's import status only. It never says "another organization already imported it" for a Private copy.
- [ ] **History grouping:** when more than one Shared copy of the same `(project, recording_id)` exists, Project History shows **one** meeting card (the viewer's organization's copy if it has one, else the oldest) with the hint "também importada por DIMAS" / "also imported by DIMAS". Only Shared copies are named; **Private copies are never mentioned**. Items of the copies are not merged in phase 1.
- [ ] **Storage:** evaluate reusing the object (server-side copy or a shared key with a reference count) instead of storing the video twice. Phase 1 may ship with duplication if reuse needs more than a small change; document the choice and the cost (~$1/month per 100 meetings on R2, 13.1).
- [ ] Deleting one copy never deletes an object another copy uses (independent keys are already safe; with reuse, a reference count).
- [ ] 12.4 Security finding 4 is marked closed with a pointer here.
- [ ] Tests: souBIM and DIMAS import the same recording into the same project, both succeed; each sees only its own copy while Private; both Shared → one card with the hint; same organization twice → 409; nothing returned to DIMAS reveals souBIM's Private copy (409, listing, retry, History hint); deleting one copy leaves the other and its recording intact.
- [ ] User-facing note: two copies of the same meeting may extract differently, each shows its own model/version (13.6, 13.7).

## Dev Notes

- **Affected code:** `app/services/fathom_import.py` (duplicate check, create import), `app/api/routes/fathom.py` (`already_imported`, listing, `import_visible`), `app/database/models.py` (`FathomImport` constraint), the History grouping in the frontend (`Timeline.tsx`, `SourceGroupAccordion.tsx`, `buildMeetingGroups()`), a backend field `also_imported_by` (Shared copies only, computed with `visible_sources_filter`), the status chip on the `FathomMeetings` page.
- **Webhook (13.9):** runs per connection's organization, so it should work with the new constraint. Verify there is no idempotency check on `(project, recording)` alone.
- **Grouping key:** both copies come from Fathom's transcript, so grouping by `recording_id` is reliable. Manual uploads have no `recording_id` and are never grouped.
- **No reconciliation of the two extractions in phase 1.**
- **Risks:** the grouping adds a join on History queries (check performance on large projects). The hint must never name an organization whose copy is Private.

## Out of scope (phase 2)

- Option (b): one canonical meeting with per-organization extraction versions.
- Merging or deduplicating items across copies; a "compare the two extractions" view.
- Reference-counted object sharing, if phase 1 ships with duplication.
- Cross-organization notifications ("DIMAS imported this meeting").
- Dedup of manual uploads of the same file.
