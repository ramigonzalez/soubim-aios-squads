# Story 12.9 — Per-Organization Google Drive

**Story ID:** 12.9
**Epic:** E12 — Organizations & Client Access
**Priority:** Medium | **Effort:** 5–8 SP (estimate, depends on the scope decision below)
**Status:** Draft
**Type:** Feature (integration, security)
**Requested by:** Rami — white-label organization admins connect their **own** Google Drive and pick only their own folders

---

## Goal

Today every project's Drive monitoring (10.3) and curation upload (7.7) go through **one shared souBIM service account** (`GOOGLE_DRIVE_SERVICE_ACCOUNT_KEY`). Since 12.2 (fix F2), only souBIM platform admins may set `projects.drive_folder_id`, because any folder id would be read with souBIM's credentials.

This story lets an **organization admin connect their organization's Google Drive via OAuth** ("Conectar Google Drive") and choose the folder for each of their projects **from that connection only**. Documents are then read (and curation files written) with **the organization's own credentials**, so an admin can never reach souBIM's (or another organization's) folders. The service account stays for souBIM's own projects until they are migrated.

## Acceptance Criteria (draft)

- [ ] `google_drive_connections`: `organization_id` (unique — one per organization), `connected_by` (user), `account_email`, `refresh_token_enc` (Fernet, 13.3 `app/utils/crypto.py`), `scopes`, `connected_at`, `revoked_at` (= needs reconnect)
- [ ] Connect flow for **owner/admin of the active organization**, reusing the 13.3 pattern:
  - signed, single-use `state` naming user + organization;
  - public callback that parks the tokens as *pending*;
  - authenticated confirm by the same user;
  - PKCE;
  - `access_type=offline`, `prompt=consent` (a refresh token is needed);
  - `include_granted_scopes=true`.
- [ ] Settings → Integrations: "Google Drive" card per organization: status, connected account, "Conectar" / "Reconectar" / "Desconectar" (revokes at Google with `https://oauth2.googleapis.com/revoke` + deletes tokens)
- [ ] Folder selection with the **Google Picker** (frontend, short-lived access token minted by the backend for that organization) — the admin can only pick folders their Google account can see; the backend stores `drive_folder_id` **+ `drive_connection_id`** on the project
- [ ] Authorization: an organization admin may set `drive_folder_id` only together with **their own organization's** connection, on projects **owned** by that organization (12.3 shared projects: owner only). Platform admins keep the current service-account path (`drive_connection_id` NULL)
- [ ] `DriveMonitor` (10.3) and curation upload (7.7) pick the credentials per project: the organization connection when `drive_connection_id` is set, otherwise the service account. A connection marked needs-reconnect skips its projects and shows a warning instead of failing the whole poll
- [ ] Disconnecting (or the admin leaving the organization) stops monitoring of that organization's folders. The projects keep their already-ingested sources
- [ ] All Google Drive OAuth/HTTP calls in one client module, with tests against recorded responses (no real Google calls in CI), like `app/integrations/fathom.py`
- [ ] Migration `0NN_story_12_9`; tests for cross-organization folder hijack (the 12.2 F2 scenario with OAuth connections)

## Relation to the Google OAuth app of 12.8 (Sign in with Google)

- **Same Google Cloud project, same consent screen**. Probably a **second OAuth client** (Web application) `DecisionLog Drive` with its own redirect URI `https://<api>/api/integrations/google-drive/callback`, or the same client with an extra redirect URI. Separate clients keep secrets and redirect lists apart. Either way the consent screen (app name, verification status) is shared by the project.
- **Different scopes, requested incrementally**:
  - Sign-in asks only `openid email profile`, which are non-sensitive.
  - The Drive connect asks the Drive scopes, only from organization admins and only when they click "Conectar Google Drive". Use `include_granted_scopes=true`, so login never shows Drive permissions.
- **Scope choice drives everything**:

| Scope | Google class | What it allows | Fits? |
|-------|-------------|----------------|-------|
| `drive.file` | **Non-sensitive** (recommended) | Only files the app created or the user explicitly opened/picked with the app (Google Picker) | Curation upload: yes. Monitoring a folder: **only if picking a folder in the Picker grants access to the files later added to it** (open question 1) |
| `drive.readonly` | **Restricted** | Read every file the user can see | Monitoring: yes. Needs restricted-scope verification + yearly security assessment |
| `drive` | **Restricted** | Full read/write | More than needed |
| `drive.metadata.readonly` | Restricted | Metadata only | Not enough (needs content) |

- **Adding Drive scopes to the project's consent screen affects verification of the whole app.** While a sensitive/restricted scope is unverified, every user of the consent screen sees the "Google hasn't verified this app" warning and is capped at 100 users. Sign-in only asks basic scopes, but the 100-user cap applies to the project. If verification of a restricted scope takes long, a **separate Google Cloud project for Drive** keeps 12.8 sign-in unaffected (open question 3).

## Google verification requirements

- **Non-sensitive only (`openid email profile`, `drive.file`)**: publish the app. Brand verification (app name/logo, home page and privacy policy on a verified, owned domain, authorized domains) is needed to show the name/logo without warnings. It usually takes a few days. No security assessment.
- **Sensitive scopes**: brand verification, plus scope justification, a **demo video** of the OAuth flow and of how the data is used, and privacy policy disclosures (Google API Services User Data Policy, Limited Use). The review takes several weeks. No third-party assessment.
- **Restricted scopes (`drive`, `drive.readonly`)**: all of the above, plus a **CASA security assessment** by an authorized third-party assessor (Tier 2 at least, paid, renewed every 12 months), and the Limited Use attestation. It takes weeks to months and has a recurring cost. This is the main reason to try `drive.file` + Picker first.
- **Testing mode** (before verification): max 100 test users listed by hand. Refresh tokens of apps in Testing mode with Drive scopes **expire after 7 days**, so monitoring would break weekly. It is fine for a pilot, not for production.
- **Google Workspace clients** can also trust the app in their Admin console (App access control), which bypasses the unverified warning for their domain. That is per client, not a substitute for verification.

## Migration of the current souBIM service-account setup

1. **Phase 1 (this story): coexist.**
   - Existing projects keep `drive_folder_id` with `drive_connection_id = NULL`, so they still use the service account.
   - No data migration; the 12.2 F2 rule stays for that path (platform admin only).
2. **Phase 2 (optional, after 12.9 ships): souBIM moves to OAuth too.**
   - souBIM connects its Drive like any organization.
   - A one-off script re-points souBIM's projects to the new connection, after checking that the connected account can see each `drive_folder_id`. With `drive.file`, souBIM would re-pick the folders in the Picker.
   - Then `GOOGLE_DRIVE_SERVICE_ACCOUNT_KEY` can be removed.
3. **Keep the service account** if souBIM prefers it (no token expiry, no user dependency). It is then a platform-only feature, documented as such.
4. Curation files created by the service account stay owned by it. Files created by an OAuth connection are owned by the connecting user's Drive. Note this in the UI ("files are created in your Drive").

## Open questions

1. **Does `drive.file` + Google Picker on a folder give the app access to files added to that folder later?** This decides non-sensitive vs restricted scope. **Spike before estimating**: pick a folder with the Picker, add a file afterwards, list it via the API.
2. If a restricted scope is needed: is souBIM willing to pay for and maintain the yearly CASA assessment? Or is a **manual upload / "share the folder with our service account" model** enough for white-label clients? The alternative is that each client shares their folder with a per-organization service account, which needs no OAuth verification but is clunkier to onboard.
3. Same Google Cloud project as 12.8 sign-in, or a separate project so a pending Drive verification never affects login? (Leaning: same project while only non-sensitive scopes are used, separate if restricted.)
4. Connection ownership: per **organization** (proposed) or per **user** like Fathom (13.3)? What happens when the connecting admin leaves the organization or loses access to the folder? (Proposed: mark needs-reconnect and notify the other admins.)
5. Shared projects (12.3): only the owning organization's connection may feed a project. Should a guest organization be able to add its own folder?
6. Multiple folders per project, or subfolders? (Today: one folder, non-recursive.)
7. Do we need Shared Drives (Team Drives) support (`supportsAllDrives`, `includeItemsFromAllDrives`)? Many Workspace clients keep project files there.
8. Privacy policy and home page: which domain hosts them for the consent screen (needed for any verification)?
