# Story 12.9 — Per-Organization Google Drive (shared with our service account)

**Story ID:** 12.9
**Epic:** E12 — Organizations & Client Access
**Priority:** Medium | **Effort:** 3–5 SP (estimate)
**Status:** Draft
**Type:** Feature (integration, security)
**Requested by:** Rami — white-label organizations feed their projects from their **own** Google Drive folders

---

## Goal

Today every project's Drive monitoring (10.3) and curation upload (7.7) go through **one platform service account** (`GOOGLE_DRIVE_SERVICE_ACCOUNT_KEY`). Since 12.2 (fix F2), only platform admins may set `projects.drive_folder_id`, because any folder id would be read with the platform's credentials.

This story lets an **organization admin** feed a project from a Drive folder **without OAuth and without Google verification**:

1. The admin shares the folder with the service account e-mail (Viewer, or Editor for curation upload). The app shows that e-mail with a copy button.
2. The admin opens the project settings and **picks the folder from a list**. The list holds only the folders that **a member of their own organization** shared with the service account (Drive `sharedWithMe` + `sharingUser`). No link pasting, and no way to pick another organization's folder.
3. The existing `DriveMonitor` reads the folder with the service account, including files and subfolders added later.

## Why not OAuth (decided 2026-10-15)

- **Spike, 2026-10-15:** `drive.file` + Google Picker gives access to the picked folder itself, but **not to its contents**. `files.list` on the folder returned 0 files, including files and a subfolder added after the pick. Details are in the "Spike" section below.
- Folder monitoring through OAuth therefore needs `drive.readonly`, a **restricted** scope:
  - It requires a yearly **CASA Tier 2** assessment, about **USD 540–4,500 per year** depending on the assessor (TAC Security lists USD 540–1,800).
  - It also requires the Google restricted-scope review, which takes weeks to months.
  - Rami: no to that for now (2026-10-09, confirmed 2026-10-15).
- **Fallback (Rami):** if sharing with the service account is too annoying for clients, drop folder monitoring and use **manual upload** (13.5, already shipped).

## Acceptance Criteria (draft)

- [ ] `GET /api/integrations/google-drive/info` (any member): the service account e-mail and whether Drive is configured on the server
- [ ] `GET /api/integrations/google-drive/folders` (owner/admin of the active organization): the folders shared with the service account (`sharedWithMe and mimeType = folder`) **whose `sharingUser.emailAddress` is the e-mail of a member of the active organization**. Fields: id, name, shared by, shared at
- [ ] `PATCH /api/projects/{id}`: an owner/admin of the **owning** organization may set `drive_folder_id`. The backend checks again that the folder is in that organization's list above, otherwise it answers 403 `folder_not_shared_by_organization`. Platform admins keep the current path
- [ ] Project settings, "Google Drive" section (pt-BR):
  - the service account e-mail with a copy button;
  - a three-step how-to (open Drive, share the folder with this e-mail, come back);
  - "Atualizar lista";
  - the folder dropdown;
  - the current folder and when it was last checked;
  - "Remover pasta".
- [ ] Clear states: Drive not configured on the server; no folders shared yet; the folder is no longer shared (the monitor gets 404/403 and marks the project with a warning instead of failing the whole poll)
- [ ] `DriveMonitor` unchanged apart from the per-project warning, and only for projects of active (not blocked) organizations (12.13 A11)
- [ ] Tests:
  - the list filter (a folder shared by a non-member is hidden);
  - the PATCH re-check (the cross-organization folder hijack scenario from 12.2 F2);
  - no real Google calls in CI (recorded responses, like `app/integrations/fathom.py`).
- [ ] Production: create the service account in `decisionlog-soubim`, enable the Drive API (done 2026-10-15), set `GOOGLE_DRIVE_SERVICE_ACCOUNT_KEY` on api + worker, and document it in `docs/development/DEPLOYMENT_RAILWAY.md`

## Security notes

- The filter trusts Google's `sharingUser`, which is the account that actually shared the folder. A member can only offer folders they shared themselves.
- If a member leaves the organization, their shared folders disappear from the list, but projects already set keep monitoring them. Phase 2: re-check on each poll.
- Isolation between organizations rests on the list filter and the PATCH re-check. The service account itself sees every client's shared folder.
- Curation upload (7.7) writes with the service account. That needs **Editor** on the folder, and the files are owned by the service account. The how-to says so.

## Out of scope (phase 2+)

- OAuth Drive connection per user or organization (needs `drive.readonly` + CASA, see above)
- Push notifications (`changes.watch`) instead of polling
- Shared Drives (Rami, 2026-10-09: not yet)
- One service account per organization
- Gmail per organization (7.4 has the same shared-credential problem)

## Spike: `drive.file` + Picker (2026-10-15)

- **Setup:**
  - Rami's Google account, in Testing mode;
  - the OAuth client "DecisionLog Web" with origin `http://localhost:8765`;
  - Picker with `setAppId(962197713000)`, `DocsView(FOLDERS).setSelectFolderEnabled(true)`;
  - a browser key restricted to the Picker API and `localhost:8765`.
- **Result:**
  - `drive.file` was granted.
  - After picking `Promem - Test`, `files.get` on the folder answers 200 (`canListChildren: true`).
  - `files.list` with `'<folder>' in parents` returned **0 files** in 17 rounds. Rami added a file to the folder, a subfolder (`uma pasta`) and a file inside it.
  - A later token did not change it.
- **Conclusion:** the Picker grants the folder object only, not its contents.
- **Leftovers:**
  - API key `Picker spike (localhost)` (uid `87801257-9960-4bf0-a610-ea146305b89e`), harmless and can be deleted;
  - the `http://localhost:8765` JavaScript origin on the OAuth client, which can be removed.
