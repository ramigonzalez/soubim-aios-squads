# Story 12.3 — Project Sharing Between Organizations

**Story ID:** 12.3
**Epic:** E12 — Organizations & Client Access
**Priority:** High | **Effort:** 5 SP (estimate)
**Status:** Ready for Review

## Description

A project like D/SEASON involves souBIM (architecture) and DIMAS (construtora). The owning organization can **share a project with another organization** at an access level. Members of the invited organization then see the project and its **shared** meetings (12.4).

## Acceptance Criteria

- [x] `project_organizations`: project_id, organization_id, access (`owner` / `contributor` / `viewer`), invited_by, created_at; the owner org has an `owner` row (migration `010_story_12_3` backfills one per project; project creation adds it)
- [x] Owner-org admins can invite an organization to a project, change its access, remove it
- [x] `contributor` can add meetings/items to the project; `viewer` only reads
- [x] Project Edit page: "Organizações com acesso" section (list, invite, change, remove)
- [x] Removing an organization immediately removes its access (covered by 12.2 isolation tests — `TestProjectSharing` in `tests/unit/test_org_isolation.py`)

## Dev Notes

- Invitation target: an existing organization (by name/slug) for now; inviting a company that has no account yet goes through 12.5 invitations.
- `project_participants` (discipline roster) stays as is — it describes who attends meetings, not who has app access. Consider linking a participant to a user later.
- Open decision: can an invited organization re-share the project with a third one? (Proposal: no — only the owner org.) → implemented as proposed.

## Access rules (implemented)

Extends the 12.2 table (`app/services/access.py`, `project_access_level` / `accessible_projects_filter`):

| Who | Level on a project |
|-----|--------------------|
| `owner` / `admin` of the owning organization | `admin` (unchanged) |
| `member` of the owning organization assigned to the project | `write` (unchanged) |
| `owner` / `admin` of an organization the project is shared with | `contributor` → `write`, `viewer` → `read` |
| `member` of a shared organization **and** assigned to the project (`project_members`) | same shared level |
| anyone else | `none` |

A shared organization never gets `admin`: it cannot edit/archive the project, toggle milestones, approve ingestion, create share links or manage organizations (no re-sharing). Ownership stays `projects.owner_organization_id`; the `owner` row mirrors it and never grants access by itself.

## API (implemented)

All endpoints need `admin` on the project (owner/admin of the owning organization): 404 project missing, 403 otherwise.

| Endpoint | Behaviour |
|----------|-----------|
| `GET /api/projects/{id}/organizations` | `{organizations: [owner, ...shares oldest first]}` — `organization_id, name, slug, access, invited_by, created_at` |
| `POST /api/projects/{id}/organizations` | body `{organization_slug \| organization_id, access: contributor\|viewer}` → 201; 404 unknown organization, 400 owner organization, 409 already shared, 422 no target / invalid access |
| `PATCH /api/projects/{id}/organizations/{org_id}` | body `{access}`; 400 owner organization, 404 not shared |
| `DELETE /api/projects/{id}/organizations/{org_id}` | access ends immediately; 400 owner organization, 404 not shared |

## Assumptions & gaps

Each item: chosen option — alternatives — who should confirm.

1. **Invitations are `contributor` or `viewer` only; `owner` is the owning organization.** The `owner` row mirrors `projects.owner_organization_id` (NOT NULL since 12.2), which stays the single source of truth for ownership; a stray `owner` row grants nothing (tested). — Alt: co-ownership (invite as `owner` → `admin`, could manage shares) / make the table the source of truth and drop the column. — **Rami / @architect**.
2. **Shared-organization roles follow 12.2 gap 1**: the shared organization's owner/admin get the shared level on the project; its `member`s only when assigned in `project_members`. — Alt: every member of the shared organization gets the level. — **Rami**. **Gap:** there is no API/UI to assign users to a project (`project_members` is only written by project creation and the seed), so members of a shared organization cannot get access yet — needs a project-members endpoint (likely 12.5).
3. **No re-sharing** (story proposal): only owner/admin of the owning organization list/invite/change/remove; shared organizations and owner-org members get 403. — Alt: allow shared-org admins to re-share at ≤ their own level. — **Rami**.
4. **Invite target by exact slug (case-insensitive, trimmed) or id; no search/directory endpoint**, so no organization list leaks to other companies. An org admin can probe whether a slug exists (404 vs 201) — low risk, accepted. — Alt: search by name (needs a directory decision) / email-based invitation with acceptance (12.5). — **@po / Rami**.
5. **Invitation is immediate** (no acceptance step by the invited organization). — Alt: pending invitation accepted by the invited organization's admin (12.5). — **Rami**.
6. **`contributor` = 12.2 `write`**: add/edit items, participants, stages, document upload, Tactiq webhook. Admin-only actions (milestone toggle, ingestion approve/reject/retry/delete, project edit/archive, share links) stay with the owning organization. — Alt: participants/stages editable only by the owner organization. — **Rami**.
7. **Meeting visibility (Story 12.4, not implemented here):** until 12.4, a shared organization sees **every** meeting of the project — meeting viewer and recording links, items, digest, and the ingestion queue/history (incl. pending sources) of shared projects for its admins (mutations stay owner-org admin only). 12.4 must restrict these to shared meetings. — **@po** (12.4).
8. **Share list visible only to owner-org admins**; a shared organization does not see which other organizations have access. — Alt: everyone with `read` sees the list. — **@po**.
9. **Frontend:** the sharing section on Project Edit renders only when the list endpoint succeeds (hidden on 403). The Edit button itself is still gated on `user.role === 'director'` (12.2 gap 10). — **Rami** (12.5).
10. Removing a share keeps the removed organization's users' `project_members` rows (harmless: no share → no access; re-sharing restores their assignment). Recording links already issued stay valid up to their 6 h TTL (12.2 F5). Public milestone share links (8.4) are unaffected.
11. **Gap — review:** @po review (epic table); @architect review of `access.py` recommended as in 12.2.
