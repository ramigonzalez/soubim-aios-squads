# Story 12.13 — Platform Admin Page (Create Organizations) and Multi-Tenancy Audit

**Story ID:** 12.13
**Epic:** E12 — Organizations & Client Access
**Priority:** High | **Effort:** 8–13 SP (estimate; the audit may produce follow-up stories)
**Status:** Draft
**Type:** Feature + security audit
**Requested by:** Rami (2026-10-09). His words: "Let's create new organizations with a new ADMIN ONLY page. Only authorized to me. We need to check all our models if they are well implemented under the multi-tenancy pattern to avoid data leaks across organizations and mixed info. This is huge." ## Story

As the **platform operator (Rami)**, I want a page that only I can open, where I create organizations and invite their first owner. I also want proof that no organization can ever see another organization's data.

## Part A — Platform admin page

### Context (current behaviour, verified in 12.12)
- "Platform admin" means owner or admin of the organization with the slug `soubim` (`access.is_platform_admin`), so every souBIM admin has it, not only Rami.
- New-company invitations are a form in TeamSettings, shown by the slug (`PLATFORM_SLUG = 'soubim'`).
- There is no signup and no script to create the first user (13.8 gap).

### Acceptance Criteria (draft)
- [ ] `users.is_platform_operator` (boolean, default false), set only by a script or migration, never by the API. Only Rami's account gets it.
- [ ] `require_platform_operator` replaces `is_platform_admin` for platform-only endpoints. The scheduler status, `POST /api/sources/sync` and new-company invites move to the operator check. The souBIM slug stops being special.
- [ ] Page `/platform` (route guarded on the frontend; every API call is checked on the backend):
  - A list of organizations: name, slug, created date, number of members and projects, last activity.
  - **Create organization** (name, slug) + **invite its first owner** (email). This reuses the 12.5 invitation flow.
  - Read-only organization detail: its members and roles. Phase 1 has no impersonation.
- [ ] Script `scripts/create_platform_operator.py EMAIL` (works on an empty production database). It creates the user if needed, prints a one-time set-password link or a generated password once, and sets the flag. This closes the 13.8 first-user gap.
- [ ] Non-operators get 403 from every `/api/platform/*` endpoint, and the navigation shows no link to the page.
- [ ] pt-BR + en; tests for the 403s, organization creation, owner invite and the script.

## Part B — Multi-tenancy audit

Goal: every table and every endpoint is scoped to the organizations the user belongs to (directly, or through project sharing 12.3 and visibility 12.4). Nothing returns or changes another organization's rows.

### Method
1. **Inventory every model** (`app/database/models.py`) and classify how it reaches an organization:
   - direct `organization_id`;
   - via project → `owner_organization_id`;
   - via source → `owner_organization_id` + `visibility`;
   - per user (Fathom connection, previews);
   - global (no tenant).
2. **Inventory every route** (`app/api/routes/*`). For each one, record which access check runs (`require_project_access`, `source_visible`, the membership checks) and whether list endpoints filter in SQL rather than after the query.
3. **Cross-tenant tests:** a fixture with two organizations (A, B) and a shared project. Each endpoint is called as B against A's ids, both private and shared, and must answer 404 or 403 with no data and no existence leak.
4. **Background paths:**
   - The worker jobs (`process_source`, `fathom_import`, `thumbnail`, `fathom_preview`).
   - The Gmail poller and Drive monitor (platform mailbox and service account).
   - Storage keys and presigned URLs.
   - Embeddings and search (pgvector), and digests.
5. **Findings** go in this story (severity, place, fix). Critical and High findings are fixed in this story; Medium and Low ones get follow-up stories.

### Acceptance Criteria (draft)
- [ ] Model and route inventory tables are in this story.
- [ ] A cross-tenant test suite covers every route. It is green, or each failure is recorded as a finding.
- [ ] Every Critical and High finding is fixed and covered by a test.
