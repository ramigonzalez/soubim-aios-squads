# Story 13.16 — Fathom Routing Rules per Project, Unassigned Meetings Inside the Ingestão List

**Story ID:** 13.16
**Epic:** E13 — Recording Ingestion
**Priority:** High | **Effort:** 5–8 SP (estimate)
**Status:** Done (merged)
**Type:** Feature (migration + webhook routing + API + frontend)
**Requested by:** Rami (2026-10-07). His words: "Since Fathom will ingest all meetings to the app, we must set a kind of rule management so we define which criteria will automatically assign projects... each project will ingest only those meetings that match the pattern automatically. If a meeting does not match a pattern, that one will become unassigned." Also: "The yellow box must not exist, that would be part of the list itself."
**Builds on:** 13.9 (webhook, Unassigned), 13.4 (import), 12.7 (Ingestão gated to owners/admins/reviewers)

---

## Story

As an **organization admin or reviewer**, I want each project to have rules that say which Fathom meetings belong to it. That way, meetings from different clients that arrive in one Fathom account go to the right project on their own. Meetings that match no rule, or more than one project, wait in the Ingestão list for me to decide.

## Context (current behaviour)

- A Fathom connection has **one default project** (`fathom_connections.auto_import_project_id`). Every webhook meeting goes there, and a missing or unusable project parks the meeting in `fathom_unassigned_meetings` with the reason `no_default_project` or `project_unavailable` (`app/services/fathom_webhook.py`, `_usable_default_project`).
- With one Fathom account and several clients, one default project sends every client's meeting to the same project.
- Unassigned meetings are shown in a separate yellow box (`FathomUnassignedList`) above the Ingestão table (PR #36). Rami wants them as rows of the table itself.

## Acceptance Criteria

### Rules (per project)
- [x] Migration: table `project_fathom_rules` (id, project_id FK cascade, field, operator, value, created_by, timestamps).
  - `field`: `title` | `participant_email` | `participant_domain`.
  - `operator`: `contains` for title; `equals` for email and domain.
  - Matching is case-insensitive and ignores surrounding whitespace.
- [x] A project matches a meeting when **any** of its rules matches (OR between rules). Phase 1 has no AND groups.
- [x] CRUD API under the project (`GET/POST/DELETE /api/projects/{id}/fathom-rules`). Only users with admin or reviewer level on the project (12.7) can call it; others get 403. Values are validated (non-empty, at most 200 characters, a domain has no `@`).
- [x] UI: a "Regras do Fathom" section in project settings (ProjectEdit). It lists the rules and lets the user add one (field, value) or remove one. pt-BR and en i18n.

### Routing on webhook arrival
- [x] Candidate projects are those the connection's user can write to that are not archived (same check as today's default project).
- [x] If **exactly one** candidate project matches, the meeting is imported into it (`start_import`, the connection's visibility). It then appears in Pendentes as a normal pending meeting, waiting for approval.
- [x] If **no project** matches, it is parked as Unassigned with reason `no_match`.
- [x] If **two or more** match, it is parked as Unassigned with reason `conflict`, and the names and ids of the matched projects are stored (new column `matched_project_ids`, json).
- [x] The default-project setting is removed from the Fathom page; routing uses only the rules (see Assumptions 1).
- [x] The rule fields are read from the webhook payload: title, plus the email and domain of each calendar invitee and of the recorder. Missing fields count as no match, never as an error.

### Ingestão list (no yellow box)
- [x] `FathomUnassignedList` and the yellow box are removed. Unassigned meetings are **rows of the Pendentes table**, mixed with sources and sorted by date.
- [x] Row status:
  - **"Sem projeto"** when the reason is `no_match`, `no_default_project` or `project_unavailable`.
  - **"Conflito"** when the reason is `conflict`, shown as a warning badge. Hovering or opening the row explains the problem, e.g. "Corresponde a 2 projetos: D/SEASON, Obra X — escolha um".
- [x] The row's project cell is a project picker. For a conflict it offers the matched projects first. The row's actions are **Importar** (enabled once a project is picked) and **Descartar** (same endpoints as 13.9).
- [x] After Importar, the row turns into the normal pending source (the row leaves at once; the source shows up when the import job has created it, as with a manual import — see Assumption 10).
- [x] Unassigned rows are counted in "N itens pendentes". The **Reunião** type filter includes them. The project filter hides them unless "Todos os projetos" is selected.
- [x] Bulk select/approve skips unassigned rows (they need a project first).
- [x] pt-BR and en i18n; the parity test stays green.

### Tests
- [x] Backend:
  - Rule CRUD and its permissions.
  - Routing: one match, no match, two matches give a conflict, an archived project or one without write access is not a candidate, case-insensitive matching, missing payload fields.
- [x] Frontend: unassigned and conflict rows in the table, import from a row, the counter, the filters.

## Dev Notes

- Routing replaces `_usable_default_project` in `fathom_webhook.py`. `_park` gets the new reasons and `matched_project_ids`.
- Webhook payload field names (`title`/`meeting_title`, `calendar_invitees[].email`, `email_domain`, `recorded_by.email`): verify them against a real delivery before coding. The unassigned table does not store the payload today, so either store the needed fields at park time or log one payload in dev.
- The table merge can be done in the frontend only: `IngestionApproval` already fetches the pending sources, and the unassigned list endpoint already exists. Map both into one row type.
- 13.13 (import per organization) changes import uniqueness. Keep the routing independent of it: routing only chooses the project.

### Implementation notes (@dev, 2026-10-07)

- **Migration `021_story_13_16`** (revises `020_story_13_15`): creates `project_fathom_rules` (FK `projects` cascade, `created_by` FK `users` SET NULL, check constraints on `field` and `operator`, index on `project_id`) and adds `fathom_unassigned_meetings.matched_project_ids` (json). `fathom_connections.auto_import_project_id` is **kept but no longer read or written** (no data loss, the downgrade restores 13.9 cleanly). Tested up → down → up on a throwaway database that was then dropped (not the dev DB).
- **Routing** (`app/services/fathom_rules.py`): candidates are the projects that have at least one rule, are not archived and that the connection's user can write to. A project matches when any of its rules matches (title `contains`, email / domain `equals`; lower-case, whitespace collapsed and trimmed). `fathom_webhook.process` imports on exactly one match, parks `no_match` on none and `conflict` (with `matched_project_ids`) on two or more. `_usable_default_project` is gone.
- **Payload reading** is defensive: title from `title` or `meeting_title`; emails from `calendar_invitees[].email` and `recorded_by.email`; domains from the part after `@` plus `calendar_invitees[].email_domain` when present. Anything missing or of the wrong type is no match, never an error. **The field names still need checking against a real Fathom delivery** (Assumption 6).
- **Rule API** (`app/api/routes/fathom_rules.py`): `GET/POST /api/projects/{id}/fathom-rules`, `DELETE /api/projects/{id}/fathom-rules/{rule_id}`, all behind `require_project_access(..., REVIEW)` (project admin or assigned reviewer; others 403). POST trims the value and validates it: not empty, at most 200 characters, a domain has no `@` and no spaces, an email has exactly one `@` (422). The operator comes from the field. A duplicate (same field, same value ignoring case) is 409.
- **Unassigned list API**: each item now has `matched_projects: [{id, name}]`, resolved when listed (current names, only projects the user can still write to).
- **Auto-import settings**: `PUT /integrations/fathom/auto-import` takes `{enabled, visibility}` (a `project_id` from an old client is ignored), and the status no longer returns `project_id`/`project_name`. The Integrations page keeps the on/off toggle and the visibility; the default-project picker is gone and a line explains routing by rules. `shared` is selectable when the user can share on some project; the webhook still falls back to `internal` per meeting where the user cannot share.
- **Ingestão**: `FathomUnassignedList` (yellow box) is deleted. `IngestionApproval` merges the unassigned list (`useFathomUnassigned`, polled every 30 s) into the Pendentes rows; `UnassignedMeetingRow` shows status "Sem projeto"/"Conflito" (conflict is an amber badge; the explanation is the badge tooltip and is also written in the row), a project picker (matched projects first, in an optgroup), and Importar/Descartar on the 13.9 endpoints. Counts: the unassigned meetings are added to "N itens pendentes", the total and the Pendentes tab badge. Filters: kept by "Todos"/"Reunião", hidden by Email/Documento and by any project filter; the date filters use the meeting start (else arrival). The row checkbox is disabled and "select all" ignores the rows, so bulk approve/reject never includes them.
- **Project settings**: `FathomRulesSection` on ProjectEdit lists, adds (field + value) and removes rules; it renders nothing when the API answers 403. pt-BR and en strings added (`projects.fathomRules`, `ingestion.unassigned`); the old `integrations.unassigned` and the default-project strings were removed. Parity test green.
- **Rollout note** (Assumption 1): after deploy, every Fathom webhook meeting goes to Unassigned until projects have rules. Tell admins/reviewers to add rules under each project's settings (Editar projeto → Regras do Fathom). The old default project is not converted.
- **Tests**: backend `tests/unit/test_fathom_rules.py` (CRUD, validation, 403s for member / unassigned reviewer / other organization, matching, routing: one / none / two matches, archived and no-write projects are not candidates, case-insensitive, missing payload fields, assigning a conflict); `tests/unit/test_fathom_webhook.py` moved from the default project to rules. Frontend: `IngestionApproval.test.tsx` (unassigned/conflict rows, order, counter, picker order, import, error, discard, type/project/date filters, bulk select, empty state), `FathomRulesSection.test.tsx`, `FathomAutoImport.test.tsx` (no picker).
- **Results**: backend CI command 1017 passed, 1 skipped, 67 deselected (known failures). Frontend: typecheck clean, lint 0 errors (3 old warnings in files not touched), vitest 695 passed, 2 skipped.

## Assumptions & gaps (pending confirmation)

1. **Decided (Rami, 2026-10-07): the default project is removed.** No match always means Unassigned, which avoids sending a meeting to the wrong client. Existing connections that have a default project: migrate it into a rule? There is nothing to convert it to, so the rollout note tells admins to add rules. 
2. **Rule fields in phase 1** are title contains, participant email and participant domain. Alternatives: the recorder's email only, or a calendar or Fathom team name. — **Rami/@po**
3. **Decided (Rami, 2026-10-07): project admins and reviewers edit rules** (the same people who work Ingestão).
4. **A conflict is never resolved automatically** (Rami, 2026-10-07: "should go unassigned with a warning message or in a conflict status explaining the multiple match"). Decided.
5. **Rules are per project** (Rami, 2026-10-07). Decided.
6. **Webhook payload field names are not verified** (`title`/`meeting_title`, `calendar_invitees[].email`, `calendar_invitees[].email_domain`, `recorded_by.email`). They are read defensively, so a wrong name gives "no match" (the meeting waits in Ingestão), never an error. Check them against a real delivery before relying on email/domain rules. Alternative: log one payload in dev, or store the payload's people at park time. — **@dev/Rami**
7. **Conflict projects are stored as ids only**; names are read when the list is loaded, limited to projects the user can still write to (a renamed project shows its new name; a project the user lost access to is not shown). Alternative: store a name snapshot with the ids. — **@po**
8. **Exactly one match but recording storage not configured**: parked as `project_unavailable` ("Sem projeto") with the match stored, so the picker offers it first. Alternative: create the import anyway and let it fail. — **@dev**
9. **Resolved (Rami, 2026-10-07): reviewers' entry point to the rules.** Reviewers who are not admins see a "Regras do Fathom" button on the project page (`can_review` and not `can_manage`), which opens `/projects/{id}/edit`. There they see only the rules section; the project form and sharing stay admin-only (`can_manage`).
10. **After Importar the row leaves at once**; the pending source appears when the import job has downloaded the recording (same as a manual 13.4 import), so there can be a short gap. Alternative: show an "importing" placeholder row until the source exists. — **@po**
11. **Order of the Pendentes rows**: the existing grouping is kept (meetings, then emails, then documents) and each group is now sorted newest first; unassigned meetings sit among the meetings by start date. Alternative: one date order across all types. — **@po**
12. **Counts**: the unassigned meetings are added to "N itens pendentes", the total and the Pendentes tab badge (all unfiltered, like the backend `pending_count`). The navigation badge (`usePendingCount`) is unchanged. Alternative: add them to the nav badge too. — **@po**
13. **Visibility without a default project**: one visibility for all routed meetings; `shared` can be picked when the user can share on any project and falls back to `internal` per meeting where they cannot. Alternative: visibility per rule or per project. — **@po**
14. **Duplicate rules** (same field and value, ignoring case and surrounding spaces) are refused with 409. — **@dev**
