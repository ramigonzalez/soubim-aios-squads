# Story 13.16 — Fathom Routing Rules per Project, Unassigned Meetings Inside the Ingestão List

**Story ID:** 13.16
**Epic:** E13 — Recording Ingestion
**Priority:** High | **Effort:** 5–8 SP (estimate)
**Status:** In Progress
**Type:** Feature (migration + webhook routing + API + frontend)
**Requested by:** Rami (2026-10-07). His words: "Since Fathom will ingest all meetings to the app, we must set a kind of rule management so we define which criteria will automatically assign projects... each project will ingest only those meetings that match the pattern automatically. If a meeting does not match a pattern, that one will become unassigned." Also: "The yellow box must not exist, that would be part of the list itself."
**Builds on:** 13.9 (webhook, Unassigned), 13.4 (import), 12.7 (Ingestão gated to owners/admins/reviewers)

---

## Story

As an **organization admin or reviewer**, I want each project to have rules that say which Fathom meetings belong to it. That way, meetings from different clients that arrive in one Fathom account go to the right project on their own. Meetings that match no rule, or more than one project, wait in the Ingestão list for me to decide.

## Context (current behaviour)

- A Fathom connection has **one default project** (`fathom_connections.auto_import_project_id`). Every webhook meeting goes there, and a missing or unusable project parks the meeting in `fathom_unassigned_meetings` with the reason `no_default_project` or `project_unavailable` (`app/services/fathom_webhook.py`, `_usable_default_project`).
- With one Fathom account and several clients, one default project sends every client's meeting to the same project.
- Unassigned meetings are shown in a separate yellow box (`FathomUnassignedList`) above the Ingestão table (PR #36). Rami wants them as rows of the table itself.

## Acceptance Criteria

### Rules (per project)
- [ ] Migration: table `project_fathom_rules` (id, project_id FK cascade, field, operator, value, created_by, timestamps).
  - `field`: `title` | `participant_email` | `participant_domain`.
  - `operator`: `contains` for title; `equals` for email and domain.
  - Matching is case-insensitive and ignores surrounding whitespace.
- [ ] A project matches a meeting when **any** of its rules matches (OR between rules). Phase 1 has no AND groups.
- [ ] CRUD API under the project (`GET/POST/DELETE /api/projects/{id}/fathom-rules`). Only users with admin or reviewer level on the project (12.7) can call it; others get 403. Values are validated (non-empty, at most 200 characters, a domain has no `@`).
- [ ] UI: a "Regras do Fathom" section in project settings (ProjectEdit). It lists the rules and lets the user add one (field, value) or remove one. pt-BR and en i18n.

### Routing on webhook arrival
- [ ] Candidate projects are those the connection's user can write to that are not archived (same check as today's default project).
- [ ] If **exactly one** candidate project matches, the meeting is imported into it (`start_import`, the connection's visibility). It then appears in Pendentes as a normal pending meeting, waiting for approval.
- [ ] If **no project** matches, it is parked as Unassigned with reason `no_match`.
- [ ] If **two or more** match, it is parked as Unassigned with reason `conflict`, and the names and ids of the matched projects are stored (new column `matched_project_ids`, json).
- [ ] The default-project setting is removed from the Fathom page; routing uses only the rules (see Assumptions 1).
- [ ] The rule fields are read from the webhook payload: title, plus the email and domain of each calendar invitee and of the recorder. Missing fields count as no match, never as an error.

### Ingestão list (no yellow box)
- [ ] `FathomUnassignedList` and the yellow box are removed. Unassigned meetings are **rows of the Pendentes table**, mixed with sources and sorted by date.
- [ ] Row status:
  - **"Sem projeto"** when the reason is `no_match`, `no_default_project` or `project_unavailable`.
  - **"Conflito"** when the reason is `conflict`, shown as a warning badge. Hovering or opening the row explains the problem, e.g. "Corresponde a 2 projetos: D/SEASON, Obra X — escolha um".
- [ ] The row's project cell is a project picker. For a conflict it offers the matched projects first. The row's actions are **Importar** (enabled once a project is picked) and **Descartar** (same endpoints as 13.9).
- [ ] After Importar, the row turns into the normal pending source.
- [ ] Unassigned rows are counted in "N itens pendentes". The **Reunião** type filter includes them. The project filter hides them unless "Todos os projetos" is selected.
- [ ] Bulk select/approve skips unassigned rows (they need a project first).
- [ ] pt-BR and en i18n; the parity test stays green.

### Tests
- [ ] Backend:
  - Rule CRUD and its permissions.
  - Routing: one match, no match, two matches give a conflict, an archived project or one without write access is not a candidate, case-insensitive matching, missing payload fields.
- [ ] Frontend: unassigned and conflict rows in the table, import from a row, the counter, the filters.

## Dev Notes

- Routing replaces `_usable_default_project` in `fathom_webhook.py`. `_park` gets the new reasons and `matched_project_ids`.
- Webhook payload field names (`title`/`meeting_title`, `calendar_invitees[].email`, `email_domain`, `recorded_by.email`): verify them against a real delivery before coding. The unassigned table does not store the payload today, so either store the needed fields at park time or log one payload in dev.
- The table merge can be done in the frontend only: `IngestionApproval` already fetches the pending sources, and the unassigned list endpoint already exists. Map both into one row type.
- 13.13 (import per organization) changes import uniqueness. Keep the routing independent of it: routing only chooses the project.

## Phase 2+ (documented, not built)

- Apply rules to meetings that are already unassigned (a "re-route" button).
- AND conditions inside a rule; rule priority or ordering to resolve conflicts automatically.
- AI suggestion of a project when no rule matches.
- Rules for other sources (email, documents).
- Rules defined per Fathom connection instead of per project.
