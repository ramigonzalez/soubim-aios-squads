# Story 13.7 — Extraction Versions & Rollback

**Story ID:** 13.7
**Epic:** E13 — Recording Ingestion
**Priority:** Medium | **Effort:** 5 SP (estimate)
**Status:** Ready for Review
**Type:** Feature
**Requested by:** Rami — "sometimes we liked something from a previous version and the new import overwrites that"

---

## Description

Re-extracting a meeting (new prompt, new model) replaces its items (`--replace` in Story 7.10). Keep **every extraction as a version** of the meeting and let a user switch the active version back.

## Acceptance Criteria (draft)

- [x] `extraction_runs`: source_id, version number, model, prompt hash/version, created_by, created_at, raw output JSON, meeting_summary, item counts, is_active
- [x] Items belong to a run; History and the viewer show only the active run's items
- [x] Re-extract creates a new run (active by default) without deleting the previous one
- [x] "Versões" in the meeting header: list runs (model, date, items count), activate one, compare counts
- [x] Import script and `extract` job (13.6) both create runs

## Dev Notes

- Reviews (12.6) belong to a run; switching runs shows that run's review state. Carrying approvals across runs is out of scope.
- The D/SEASON pilot already produced three versions worth keeping as examples (`outputs/v1-english`, `v2-pt`, current).

## Blocked By

13.6.

## Implementation Notes

- `extraction_runs` (migration `014_story_13_7`): source, version, model, prompt hash, status, tokens in/out, `meeting_summary`, `raw_output` (validated items), `is_active`; partial unique index = one active run per source. `project_items.extraction_run_id` (NULL = manual / email / document items, always shown).
- Backfill: each source's existing items become version 1, active (D/SEASON keeps its 54 items). Verified up/down/up on a throwaway DB; downgrade drops the items of inactive versions.
- `app/services/extraction_runs.py`: `active_items_filter()` (applied to the items list, facets, milestones, search, V1 decisions, project counts/stats, shared timeline and ingestion history counts), `create_run`, `activate_run`.
- Runs are created by the worker (`process_approved_source`) and by `import_items` (import script; `--replace` now means "new version", nothing is deleted; `--model` records the model).
- API: `GET /sources/{id}/extraction-runs` (any reader, with `can_manage`, counts by type, tokens, latest job), `POST /sources/{id}/extraction-runs/{run}/activate` (admin, atomic, restores the version's summary), `POST /sources/{id}/re-extract` (admin; queues `process_source` with `re_extract`, the source stays `processed` if it fails).
- Frontend: "Versões" panel (`ExtractionVersions`) in the meeting viewer header; pt-BR + en.

## 12.4 integration

Every item listing applies visibility (`visible_items_filter` / `public_items_filter`) AND the active run (`active_items_filter`). The new endpoints use `require_source_access`: another organization's internal meeting returns 404 for list, activate and re-extract; on a shared meeting readers of other organizations can list versions (`can_manage` false) but activate / re-extract return 403. Activate and re-extract need project admin on the meeting, the same rule as approve / retry (12.4 assumption 6), not `can_change_visibility`. Public share links show shared meetings only (unchanged).
